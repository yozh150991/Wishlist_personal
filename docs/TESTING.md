# Стратегія тестування

## Рівні

| Рівень | Інструмент | Що покриває |
|---|---|---|
| БД / RLS | pgTAP (SQL) | політики доступу, інваріанти приватності |
| Парсер | pytest | витяг даних, SSRF-захист, ліміти |
| E2E | Playwright + TypeScript | сценарії користувача і гостя |

## Тести RLS — найважливіші

Пишуться першими, бо перевіряють суть продукту. Мінімальний набір:

1. Користувач A не читає списки користувача B (`select` повертає 0 рядків, не помилку).
2. Користувач A не додає позицію в список B.
3. Anon не читає `items`, `lists`, `shares` напряму — жодним запитом.
4. **Власник не читає `reservations`** — ні `select`, ні через JOIN, ні через будь-яку RPC.
5. `get_shared_list` з відкликаним токеном кидає `revoked`.
6. `get_shared_list` з простроченим токеном кидає `expired`.
7. `get_shared_list` не повертає позиції зі статусом `purchased`/`gifted`.
8. При `hide_prices: true` поле `price` дорівнює `null` у відповіді.
9. `create_share` ігнорує id позицій з чужого списку.
10. Власник, автентифікований, отримує `reserved_qty: null` (ADR-009).

## E2E-сценарії (Playwright)

**Автентифікація**
- Неавтентифікований відвідувач `/lists` → редірект на `/login?next=/lists`.
- Після входу — повернення на `?next`.
- F5 на захищеній сторінці не викидає на логін (перевірка на скелетон, а не редірект під час завантаження сесії).
- `next` з іншим хостом (`https://…`, `//…`, `/\…`) ігнорується, перехід іде на `/lists`. Покрито чистим тестом `safeNext` без браузера.

**Позиції**
- Додавання вручну лише з назвою — успішно, ціна порожня.
- Додавання за посиланням (парсер замокано) — поля заповнені, користувач може їх змінити.
- Парсер повернув 504 — форма відкрилася, додавання не заблоковано.
- Скрол: 30 позицій, розмір партії 25 → після скролу видно 30, без дублів.
- Зміна розміру партії скидає курсор і перезавантажує з початку.

**Шеринг**
- Вибір 3 з 10 позицій → «Поділитися» → у гостьовому вікні (новий browser context, без cookies) видно рівно 3.
- Головний список за прямим URL для гостя недоступний.
- Видалення позиції у власника → зникає у гостя після перезавантаження.
- Відкликання посилання → гість бачить «Посилання недоступне».

**Бронювання**
- Гість бронює → бачить «заброньовано». Другий гість (інший context) бачить те саме.
- Власник відкриває своє посилання → бачить банер і **не бачить** броней.
- Кількість 1, один гість забронював → другий отримує `not_enough_left`.

**Експорт/імпорт**
- Експорт CSV → імпорт у порожній список → кількість і суми збігаються.

## Тести парсера (pytest)

- SSRF: `http://127.0.0.1`, `http://169.254.169.254/`, `http://192.168.1.1`, DNS-rebinding (домен, що резолвиться в приватну IP) → `403`.
- Редірект з публічного домену на приватну IP → `403`.
- Сторінка > 2 МБ → `413`.
- HTML без розмітки → `200` з `partial: true` і назвою з `<title>`.
- Фікстури HTML: JSON-LD, microdata, OpenGraph, «нічого» — по одній на кожен шлях витягу.

## Запуск

```bash
supabase test db          # pgTAP
cd services/parser && pytest
cd app && npx playwright test
```

CI (GitHub Actions): підняти Supabase локально → міграції → pgTAP → зібрати фронт → Playwright. PR не мержиться з червоними тестами.

## Тестові дані

Сід у `supabase/seed.sql`: два користувачі (A і B), у A — список на 60 позицій (для пагінації), список з подією в минулому (для підсумків), активний шер і відкликаний шер. Це дає всі граничні випадки без ручної підготовки.
