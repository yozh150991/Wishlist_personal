# Стратегія тестування

## Рівні

| Рівень | Інструмент | Що покриває | Стан |
|---|---|---|---|
| БД / RLS | pgTAP (SQL) | політики доступу, гранти, інваріанти приватності | є |
| Парсер | pytest | витяг даних, SSRF-захист, перевірка токена | є |
| Фронтенд, чиста логіка | Playwright без браузера | функції без DOM (`safeNext`) | є |
| E2E | Playwright + TypeScript | сценарії користувача і гостя | є частково |

Інваріанти приватності перевіряються на рівні бази, до будь-якого фронтенду: `supabase/tests/database/`.

## Тести бази (pgTAP) — найважливіші

Три файли в `supabase/tests/database/`, 60 перевірок. Кожен файл — окрема транзакція з `rollback`, тож дані тестів не лишаються. Запускаються лише проти локальної бази.

```powershell
npx supabase start       # Docker Desktop має бути запущений
npx supabase db reset    # міграції з нуля
npx supabase test db
```

**`01_schema_guards.test.sql` — схема загалом.** Ці тести падають на *майбутній* міграції, яка щось забула:
- кожна таблиця в `public` має RLS;
- `anon` не має жодних прав на жодну таблицю чи вʼю (§3.3) — зокрема на нову, створену без `revoke`;
- жодна RLS-політика не адресована `anon` чи `PUBLIC`;
- `authenticated` не має прав на `reservations`, політик на ній нуль, жодна вʼю її не читає (§3.2);
- таблицю `reservations` згадують лише `get_shared_list`, `reserve_item`, `unreserve_item` — нова функція над бронями додається в цей список свідомо;
- `anon` може виконувати рівно чотири гостьові функції, `authenticated` — їх плюс функції власника (§3.4);
- кожна `SECURITY DEFINER` функція фіксує `search_path`.

**`02_owner_isolation.test.sql` — §3.1.** Користувач B пробує дістатися до даних A: читання (0 рядків, не помилка), `list_items_page` і `list_totals` на чужому списку, зміна й видалення, додавання позиції в чужий список, перенесення своєї позиції в чужий список, створення посилання на чужий список, підкидання чужої позиції у своє посилання. Гість пробує читати кожну таблицю напряму.

**`03_sharing_and_reservations.test.sql` — гостьовий доступ і §3.2.**
- `create_share` відкидає позиції з чужого списку, порожній вибір — помилка, токен 22 символи.
- Гість бачить лише вибрані актуальні позиції; `hide_prices` не віддає ціну; `not_found`, `revoked`, `expired`.
- Бронювання: `not_enough_left`, `item_not_in_share`, `reservations_disabled`; чужий `guest_key` не знімає бронь.
- **Власник:** упізнаний у власному посиланні, `reserved_qty` — `null` на кожній позиції, бронювання вимкнене, `reservations` недоступна ні напряму, ні через JOIN, забронювати сам не може.
- Перегляди власника не рахуються; видалена й куплена позиції зникають у гостя (ADR-007).

**Як переконались, що тести ловлять порушення.** Проти копії схеми внесено шість поломок, і кожну тести помітили: політика, що відкриває броні власнику; вимкнений RLS на `lists`; нова `SECURITY DEFINER` функція над бронями; вʼю над бронями; `get_shared_list`, що показує броні власнику; нова таблиця без відкликання прав у `anon`.

**Що вже знайшли.** Перший запуск показав, що `create_share`, `list_items_page`, `list_totals` і `gen_share_token` доступні `anon`: міграція з грантами відкликала лише `PUBLIC`, а Supabase видає `anon` окремий грант на кожну функцію. Даних це не відкривало, бо функції працюють з правами викликача. Закрито міграцією `20260916220000_revoke_default_function_grants.sql`. Заодно тести показали, що `gen_share_token` не «внутрішня»: без `EXECUTE` у `authenticated` падає створення посилання.

### Акаунт для E2E

`items.spec.ts` і `sharing.spec.ts` входять під справжнім акаунтом і без `E2E_EMAIL` та `E2E_PASSWORD` пропускаються:

```powershell
$env:E2E_EMAIL = "..."; $env:E2E_PASSWORD = "..."
npx playwright test
```

Окремої тестової бази немає: тести пишуть у ту саму бойову Supabase, що й застосунок. Тому для E2E потрібен **окремий акаунт**, не особистий — сценарії створюють списки з назвами `E2E <час>`, і вони залишаються в базі.

Без `E2E_BASE_URL` тести йдуть проти `localhost:5173` і самі запускають `npm run dev`. Проти бойового фронтенду:

```powershell
$env:E2E_BASE_URL = "https://wishlist-personal.vercel.app"
```

## Тести парсера (pytest)

**SSRF** — `test_ssrf.py`
- `127.0.0.1`, `localhost`, `169.254.169.254`, `10/8`, `192.168/16`, `172.16/12`, `[::1]`, `0.0.0.0` → `BlockedHost`.
- Схеми `file`, `ftp`, `gopher` → `BlockedHost`.
- Хост, що не резолвиться → `BlockedHost`.
- Публічний хост дозволено. Єдиний тест, якому потрібна мережа.

**Токен** — `test_auth.py`, мережу заблоковано заглушкою
- Немає заголовка, порожня схема, `Basic` → `401 missing_token`.
- Кирилиця, не-ASCII байти, не три частини, зайві символи, понад 8 КБ → `401 invalid_token`, і звернення до Supabase не відбувається (ADR-023).
- Токен правильної форми доходить до Supabase.

**Витяг даних** — `test_extract.py`
- Фікстури HTML на кожен шлях витягу: JSON-LD, microdata, OpenGraph, «нічого» (`partial: true`, назва з `<title>`).
- Розбір цін у польському, англійському й українському записі, зокрема `9,99/szt.` і `299 zł.`.
- Евристика ціни: працює без розмітки, поступається розмітці, не бере «365» з «IKEA 365+» (ADR-019).
- Рекламні параметри відкидаються, змістовні лишаються (ADR-020).
- `supabase_ready` розпізнає незаповнений шаблон.

⬜ Не покрито: редирект із публічного домену на приватну IP і обрізання сторінки понад `PARSER_MAX_BYTES` — обидва шляхи потребують підміни HTTP-відповідей. Сторінка понад ліміт **не** дає `413`: вона обрізається, бо мета-теги лежать у `<head>`.

## Запуск

```powershell
npx supabase test db                    # pgTAP, потрібна локальна база

cd services\parser
pip install -r requirements-dev.txt
pytest

cd app
npm run typecheck
npx playwright test
```

⬜ CI (GitHub Actions) ще не налаштовано. Задумано: підняти Supabase локально → міграції → pgTAP → pytest → зібрати фронт → Playwright. PR не мержиться з червоними тестами. Поки CI немає, `npx supabase test db` — обовʼязковий крок перед `db push` кожної нової міграції.
