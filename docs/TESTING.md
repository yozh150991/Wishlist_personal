# Стратегія тестування

## Рівні

| Рівень | Інструмент | Що покриває | Стан |
|---|---|---|---|
| БД / RLS | pgTAP (SQL) | політики доступу, гранти, інваріанти приватності | є |
| Парсер | pytest | витяг даних, SSRF-захист, перевірка токена | є |
| Фронтенд, чиста логіка | Playwright без браузера | функції без DOM (`safeNext`) | є |
| E2E | Playwright + TypeScript | сценарії користувача і гостя | є частково |
| Палітри | `npm run check:contrast` | контраст WCAG AA у всіх шести палітрах | є |
| Словники | `npm run check:i18n` | ключі трьох мов збігаються, підстановки на місці | є |

Інваріанти приватності перевіряються на рівні бази, до будь-якого фронтенду: `supabase/tests/database/`.

## Аудит палітр (`npm run check:contrast`)

Перевірка без браузера й без бази — читає `app/src/styles/tokens.css` і рахує контраст кожної пари «фарба на фарбі», яка реально трапляється в інтерфейсі: 25 пар × 12 палітр = 300 перевірок. Пороги WCAG AA: 4,5:1 для тексту, 3:1 для нетекстових індикаторів (смужки пріоритету, кільце фокуса).

Падає на трьох речах:

1. **Недостатній контраст** — виводить пару, палітру й обидва числа.
2. **Неповна палітра** — пропущений токен тихо падає на `:root`, тобто на світлу Шавлію, і в темній схемі дає світлий значок на темній картці. Тому склад кожного набору перевіряється поіменно.
3. **Літеральний колір у коді** — будь-який hex у `src/` (`.css`, `.ts`, `.tsx`), крім `tokens.css`. Захардкоджений колір виглядає правильно рівно в одній палітрі, а в решті одинадцяти тихо ламається. Єдиний інший джерело кольору — генератор оформлень `src/lib/hue-ramp.js`, і його перевіряє другий прогін нижче.

Другий прогін — **оформлення списків** (ADR-034): крок відтінку 15° × 2 теми = 48 рядків, кожен поверх п'яти схем смаку по 8 пар, які чіпає оверлей (посилання на фоні й поверхні, підпис головної кнопки, значок «Високий», активна пігулка, гостьовий заголовок, смужка «Високий» на гостьовій картці, кільце фокуса). Рампу рахує той самий `src/lib/hue-ramp.js`, що й застосунок: зсунутий анкер світлості валить прогін.

Додаєш палітру — вона потрапляє в прогін сама. Додаєш пару кольорів у компонентах — внеси її в `PAIRS`, інакше вона лишиться неперевіреною. У CI скрипт стоїть перед збіркою: зламаний контраст видно за секунди, а не після build.

## Словники (`npm run check:i18n`)

Теж без браузера: читає три `app/src/i18n/*.json` і всі виклики `t('…')` у `src/`. Падає на трьох речах:

1. **Ключ є не в усіх мовах** — пропущений ключ показує людині чужу мову посеред свого екрана.
2. **Підстановки розійшлися** — `{n}` у `uk` і `{count}` у `pl` означає, що в польській число не підставиться.
3. **Ключ із підстановкою викликано без значень** — `t('settings.signedInAs')` замість `t('settings.signedInAs', { email })` друкує в інтерфейс дужки з назвою змінної. Ні типи, ні збірка, ні тести цього не бачать: рядок валідний, просто безглуздий.

Саме третє й сталося з підписом у бічній колонці — його знайшли очима на ARIA-знімку впалого тесту, а не перевіркою.

## Тести бази (pgTAP) — найважливіші

Три файли в `supabase/tests/database/`, 60 перевірок. Кожен файл — окрема транзакція з `rollback`, тож дані тестів не лишаються. Запускаються лише проти локальної бази.

```powershell
npx supabase start       # Docker Desktop має бути запущений
npx supabase db reset    # міграції з нуля
npx supabase test db
```

**`01_schema_guards.test.sql` — схема загалом.** Ці тести падають на *майбутній* міграції, яка щось забула:
- кожна таблиця в `public` має RLS;
- `anon` не має жодних прав на жодну таблицю чи вʼю (§3.3) — зокрема на нову, створену без `revoke`;
- жодна RLS-політика не адресована `anon` чи `PUBLIC`;
- `authenticated` не має прав на `claims`, `guest_identities`, `guest_keys`, `guest_code_attempts`, політик на них нуль, жодна вʼю їх не читає (§3.2);
- таблицю `claims` згадують лише `get_shared_list`, `claim_item`, `release_claim`, `redeem_guest_code` і сліпе `release_item_claims` — нова функція над позначками додається в цей список свідомо;
- `anon` може виконувати рівно чотири гостьові функції, `authenticated` — їх плюс функції власника (§3.4);
- кожна `SECURITY DEFINER` функція фіксує `search_path`.

**`02_owner_isolation.test.sql` — §3.1.** Користувач B пробує дістатися до даних A: читання (0 рядків, не помилка), `list_items_page` і `list_totals` на чужому списку, зміна й видалення, додавання позиції в чужий список, перенесення своєї позиції в чужий список, створення посилання на чужий список, підкидання чужої позиції у своє посилання. Гість пробує читати кожну таблицю напряму.

**`03_sharing_and_reservations.test.sql` — гостьовий доступ, позначки й ключ гостя (§3.2, §3.3, ADR-035).** Імʼя файлу лишилось історичним.
- `create_share` відкидає позиції з чужого списку, порожній вибір — помилка, токен 22 символи.
- Гість бачить лише вибрані актуальні позиції; `hide_prices` не віддає ціну.
- **Мертве посилання — одна відповідь:** неіснуючий, відкликаний і протермінований токен дають той самий `not_found`, і позначка на відкликаному — теж.
- Позначки: перша тихо створює код із 5 символів; `not_enough_left`, `item_not_in_share`, `reservations_disabled`, `bad_key`; чужий ключ не знімає позначку; гість без ключа бачить «взято», автор позначки впізнаний; у відповіді гостю немає ні хто, ні коли — рівно 14 полів позиції; часткова кількість «1 з 2» працює й не перевищує потрібного.
- **Ключ зі списку A в списку B не впізнається** й не повертає позначок.
- **Код:** невідомий — `code_not_found`; правильний переносить позначки на новий пристрій, старий лишається робочим; вдруге той самий код не спрацьовує; після п'яти спроб за годину — `too_many_attempts` навіть на правильний.
- **Власник:** упізнаний у власному посиланні, `taken_qty`/`mine_qty` — `null` навіть із ключем гостя, позначки вимкнені; `claims`, `guest_identities`, `guest_keys` недоступні ні напряму, ні через JOIN; позначити сам не може. **`list_items_page` і `list_totals` власника байт у байт однакові до й після зміни позначки гостя.**
- **Сліпе скидання:** на позиції з позначкою й без — однаково, без помилки; тип відповіді `void`; чужу позицію скинути не можна; гість до функції доступу не має; після скидання позиція вільна.
- Перегляди власника не рахуються; видалена й куплена позиції зникають у гостя (ADR-007).

**`05_appearance.test.sql` — схеми смаку, висока контрастність і оформлення списку (ADR-033, ADR-034).** Вугіль не записується в `profiles.scheme` (лише через `high_contrast`), контраст не перезаписує смак, гість отримує `owner_scheme`, але не контраст власника, `anon` не читає профілі напряму. Оформлення: вбудовані видно кожному, чужі — ні; назва довша за 24 символи, емодзі й відтінок поза 0–359 не приймаються; вбудовану подію власник створити не може; на чуже оформлення не послатися навіть із вгаданим id; гість отримує відтінок, але не назву; `anon` не читає `appearances`; видалення лишає списку `null`.

**`06_sections.test.sql` — розділи й ручний порядок (ADR-036).** Власника розділу ставить база; назва довша за 60 не приймається; розділ іншого списку до позиції не причепити; `reorder_items` задає порядок; інший користувач не бачить чужих розділів, не додає свої в чужий список, а його `reorder_items` / `reorder_sections` нічого не змінюють; гість бачить ручний порядок (розділи за порядком, «Інше» в кінці) і лише розділи зі спільними позиціями; перестановка розділів міняє порядок у гостя; `anon` не читає розділи й не впорядковує; видалення розділу не видаляє позицій і лишає їм `null`.

**`07_share_expiry.test.sql` — термін посилання в зоні власника (ADR-037).** День + зона дають 23:59:59 цього дня за зоною власника: Київ узимку й улітку (літній час), Ванкувер (доба закінчується вже наступного дня за UTC); ICU-імена браузера `Europe/Kiev` і `Asia/Calcutta` записуються як `Europe/Kyiv` і `Asia/Kolkata`; сьогоднішня дата — ще живе посилання; старий `p_expires_at` працює без зони; неіснуюча зона, POSIX-зсув `+3` і день без зони — `bad_time_zone`; вчорашній день і момент у минулому — `expires_in_past`; довільний рядок чи зону без моменту не записати й напряму (check); гість отримує `expires_at` і `expires_tz`; посилання, чия доба скінчилась, — той самий `not_found`.

**`08_owner_side_channels.test.sql` — побічні канали власника (ADR-038).** Власник отримує `owner_cannot_reserve` з `release_claim` однаково для взятої й вільної позиції; `id` взятої й вільної позиції, як і `id` списку, не змінюється — з тією самою помилкою `immutable_column`, а не помилкою зовнішнього ключа `claims`; решта полів позиції змінюється як раніше; посилання не переписати ні на чужий, ні на свій інший список, а відкликання працює; 200 кодів гостя поспіль — пʼять символів з алфавіту без схожих знаків.

**`09_item_drafts.test.sql` — чернетки позицій (ADR-046).** Усталено позиція — не чернетка. Чернетка з адресою замість назви не потрапляє в посилання ні через `create_share` (названі позиції з того самого вибору — так), ні прямою вставкою в `share_items`, і гість її не бачить. Позиція не стає чернеткою після створення. Зміна ціни позначку лишає, а нова назва (як у v1) чи явне `needs_title = false` (як у v2) знімає. Названа колишня чернетка вже йде в посилання.

**`10_yearly_lists.test.sql` — щорічні свята (ADR-047).** Усталено список не щорічний, позначка не буває порожньою, чужий список щорічним не зробити, власник вмикає її сам.

**`13_item_currency.test.sql` — валюта позиції й курс НБП (ADR-051).** Усталено валюти в позиції немає; незнайому не записати; сума v1 (`list_totals`) — лише у валюті списку, а кількість — усі позиції; гість отримує валюту кожної позиції, розгорнуту з валюти списку, а валюта списку у відповіді лишається; курс пише й оновлює лише сервіс, злотого в таблиці немає, будь-який власник курс читає, але не змінює; гість курсу не читає. `03_sharing_and_reservations` знає `currency` серед полів позиції гостю.

**`12_notifications.test.sql` — сповіщення власника (ADR-049).** Усталено всі канали вимкнені; пояс — лише ім'я зони; чужих налаштувань не видно й не створити; напряму підписку не вставити й не видалити — лише через `save_push_subscription` і `forget_push_subscription`; адреса підписки — лише `https` і без керівних символів; ключі браузера — лише справжньої форми; чужих пристроїв не видно; та сама підписка, збережена іншим акаунтом, переходить до нього, а в попереднього зникає — спільний пристрій не бачить чужих сповіщень; понад 10 пристроїв відпадає найстаріший; «Вимкнути push тут» прибирає свій; журнал надісланого власникові недоступний, сервіс його пише; події про позначки гостей у журнал не записати. `01_schema_guards` знає `save_push_subscription` і `forget_push_subscription` серед функцій власника.

**`11_link_checks.test.sql` — перевірка посилань (ADR-048).** Усталено посилання не перевірене (`unknown` — поведінка v1); невідомого стану й валюти не з трьох великих літер не записати; роль `service_role` (так пише сервіс `wishlist-jobs`) записує висновок; зміна назви його не чіпає, а нове посилання скидає всі чотири поля. У гостьовій відповіді `get_shared_list` немає жодного ключа `link*`, і позиція з `gone` лишається видимою гостю.

**`04_item_variants.test.sql` — форма `items.variants` (ADR-030).** Обмеження `items_variants_shape` складене з вбудованих операторів jsonpath, тож помилка в одному рядку виразу тихо пропустила б сміття. Звідси матриця: приймаються порожній масив, пʼять пар, підпис рівно 40 символів, будь-який порядок ключів; відхиляються шоста пара, обʼєкт замість масиву, рядок замість пари, **вкладений масив** (він і вимагає режиму `strict`), пара без значення, зайвий ключ, нерядкове значення, підпис із самих пробілів, задовгі підпис і значення, перенос рядка. Окремо: варіанти доходять до гостя через `get_shared_list` і не ховаються разом із цінами.

**Як переконались, що тести ловлять порушення.** Проти копії схеми внесено шість поломок, і кожну тести помітили: політика, що відкриває броні власнику; вимкнений RLS на `lists`; нова `SECURITY DEFINER` функція над бронями; вʼю над бронями; `get_shared_list`, що показує броні власнику; нова таблиця без відкликання прав у `anon`.

**Що вже знайшли.** Перший запуск показав, що `create_share`, `list_items_page`, `list_totals` і `gen_share_token` доступні `anon`: міграція з грантами відкликала лише `PUBLIC`, а Supabase видає `anon` окремий грант на кожну функцію. Даних це не відкривало, бо функції працюють з правами викликача. Закрито міграцією `20260916220000_revoke_default_function_grants.sql`. Заодно тести показали, що `gen_share_token` не «внутрішня»: без `EXECUTE` у `authenticated` падає створення посилання.

- ✅ Вхід клавішею Enter повертає на сторінку з `?next`.

### Правила для сценаріїв з акаунтом

Спільні кроки — у `tests/e2e/helpers.ts`: вхід, створення списку, додавання позиції, створення посилання, вихід, відкриття фільтрів. Правила, порушення яких давало падіння — кожне коштувало окремого червоного прогону:

1. **Поля шукаються всередині відкритого діалогу** (`page.getByRole('dialog')`). Діалоги — нативні `<dialog>`, закриті лишаються в DOM, а на сторінці списку одночасно живуть форма позиції й форма списку з однаковим полем «Назва».
2. **Після відкриття діалогу — дочекатися фокусу на першому полі** (`settledDialog`). `Dialog` ставить фокус у `requestAnimationFrame`, і якщо почати введення раніше, фокус перескакує посеред нього: текст опиняється в іншому полі.
3. **Кожен тест створює дані сам.** Тести йдуть паралельно й у довільному порядку; тест, що покладається на список з іншого тесту, падає випадково.
4. **Дія, яка може законно нічого не знайти, потребує тайм-ауту.** `locator.press(..., { timeout: 1000 }).catch(() => {})` — з тайм-аутом; без нього `catch` марний, бо дія без обмеження чекає на елемент до кінця тесту й відхилення не настає ніколи. Саме так тест «Enter у діалозі створює рівно одне посилання» висів 30 секунд: перше натискання встигало створити посилання, діалог замінював форму, і друге натискання шукало вже неіснуюче поле. Під одним воркером відповідь приходила пізніше за друге натискання, і тест проходив — падати він почав лише тоді, коли набір виріс і CI пішов у два воркери.
5. **Один тест — одне перечитування вибірки.** Зміна статусу з картки й зміна фільтра запускають два незалежні запити, і тест, який чекає наслідку обох, ловить то один, то інший: у CI він падає двома різними способами на тому самому коді. Якщо для перевірки потрібен заздалегідь підготовлений стан — дочекайся запису (`waitForResponse`) і перезавантаж сторінку, а перевіряй уже саме те, заради чого тест написано.
6. **Локатор за підписом звіряється з усіма трьома словниками.** Регулярка `/^актуальні$/` не збігається з жодною мовою: в `uk.json` стоїть «Актуально». У CI, де інтерфейс англійською, такий тест проходить і мовчить про помилку.
7. **Підпис кнопки — якірний, якщо поруч є кнопки з тим самим словом.** `/filters/i` ловить не лише «Фільтри», а й «Скинути фільтри» в панелі та «Скинути всі фільтри» в стані «нічого не знайшлось». Обидві зʼявляються саме тоді, коли фільтр активний, — тобто рівно в тому стані, який тест і перевіряє. Значок кількості теж входить у назву: кнопка зветься «Фільтри 1», тож якір має пускати число.

Посилання для гостя читається з поля в діалозі, а не з буфера обміну: читання буфера потребує дозволу, якого тестовий браузер не має. Чекбокс вибору позиції шукається за роллю `checkbox` — назва позиції є і в його підписі, і в підписі списку статусу.

Перевірено проти справжніх Supabase Auth і PostgREST з міграціями й сідом: після редизайну — 210 сценаріїв на двох профілях (десктоп і Pixel 7), 208 зелених, 2 пропущено без запущеного парсера. Частина перевірок формату експорту браузера не потребує зовсім.

Набір ганяється **в обох розкладках**, і це не надмірність: телефонні падіння тут щоразу виявлялись не дрібницею локатора, а справжньою поломкою — дубльовані `id` у фільтрах, кнопка дії нижче краю екрана, кнопка виходу, якої в нижній смузі немає за задумом.

### Акаунт для E2E

`items.spec.ts` і `sharing.spec.ts` входять під справжнім акаунтом і без `E2E_EMAIL` та `E2E_PASSWORD` пропускаються. Сценарії створюють списки `E2E <час>` і залишають їх у базі, тому є два способи.

**Проти локальної бази — основний.** Дані з сіду, бойова база не страждає, `db reset` прибирає сміття:

```powershell
npx supabase db reset
$env:E2E_LOCALDB = "1"
$env:E2E_EMAIL = "anna@wishlist.test"; $env:E2E_PASSWORD = "password123"
cd app; npx playwright test
```

`E2E_LOCALDB` змушує Playwright запускати `npm run dev:local` замість `npm run dev` (потрібен `app/.env.localdb.local`, SETUP.md розділ 8). Якщо на порту 5173 вже працює звичайний `npm run dev`, Playwright використає його — і тести підуть у бойову базу. Перед запуском перевір, що звичайний dev-сервер зупинено.

**Прогрів сервера.** Перед тестами `tests/global-setup.ts` відкриває `/login` і чекає на форму входу до трьох хвилин. Playwright вважає сервер готовим, щойно той віддає `index.html`, а Vite при першому відкритті ще збирає залежності й може перезавантажити сторінку. На Windows це довше 30 секунд, і без прогріву перші паралельні тести падали на `page.goto` з тайм-аутом або `ERR_ABORTED`, а решта проходили. У консолі видно `[warm-up] dev-сервер готовий за N с`. Бойовий фронтенд (`E2E_BASE_URL`) не прогрівається.

Якщо тести з браузером усе одно масово падають на `page.goto`, запусти сервер сам у першому терміналі (`npm run dev:local`), дочекайся форми входу в браузері й запускай тести в другому — Playwright використає вже запущений сервер. Вивід Vite під час автозапуску видно в консолі тестів з префіксом `[WebServer]`. Повільну першу збірку на Windows часто спричиняє антивірус, що перевіряє кожен файл у `node_modules`; виключення теки проєкту в Defender помітно її прискорює.

Проганяй `db reset` час від часу, а не лише коли щось зламалось. Кожен прогін лишає по собі списки `E2E <час>`, і після десятка прогонів сторінка `/lists` віддає сотні карток. Тести тоді починають падати за тайм-аутом у випадкових місцях — найчастіше на створенні посилання, — і виглядає це як регресія, хоча код ні до чого.

Після `npx supabase stop` / `start` локальні ключі можуть змінитися. Якщо вхід Анни раптом перестав працювати, онови файл: `cd app; npm run env:local` — скрипт перенесе адресу й ключ із `npx supabase status` сам.

**Проти бойової бази** — лише під окремим тестовим акаунтом, не особистим:

```powershell
$env:E2E_EMAIL = "..."; $env:E2E_PASSWORD = "..."
npx playwright test
```

Проти бойового фронтенду замість локального:

```powershell
$env:E2E_BASE_URL = "https://wishlist-personal.vercel.app"
```

## PWA

Service Worker у режимі розробки вимкнено, тож E2E на dev-сервері його не бачать. Зібраний застосунок перевіряє `npm run check:pwa` (після `vite build`, у CI — задача `frontend`):
- маніфест: `name`, `display: standalone`, `start_url: /lists`;
- іконки 192 і 512 `any`, 512 `maskable`, `apple-touch-icon` 180 — PNG саме такого розміру, як заявлено;
- Service Worker відкриває адреси застосунку з `index.html`, **гостьові `/s/*` і `/l/*` виключено**, карти коду не кешуються;
- обидва гостьові префікси мають `X-Robots-Tag: noindex` у `vercel.json` і `Disallow` у `robots.txt`, а `Referrer-Policy` — одна з тих, що не віддають шлях за межі сайту (ADR-041);
- CSP у `vercel.json`: є всі ключові директиви, у `script-src` немає `'unsafe-inline'`, а хеш інлайнового скрипта теми збігається з `index.html`. Перед хешуванням кінці рядків нормалізуються до `LF`: хеш має відповідати байтам, які віддасть Vercel, а він збирає на Linux.
- Service Worker підключає `push-sw.js` (`importScripts`), а в ньому є обробники `push` і `notificationclick` (ADR-049).

### Lighthouse

Вимірюється на зібраному застосунку, не на dev-сервері:

```powershell
cd app
npx vite build --mode localdb
npx vite preview --port 4173 --strictPort
npx lighthouse http://localhost:4173/login --view
```

Стан на кінець етапу 6 (мобільна емуляція, як у Lighthouse за замовчуванням):

| Сторінка | Швидкодія | Доступність | Практики | SEO |
|---|---|---|---|---|
| `/login` | 98 | 100 | 100 | 100 |
| `/s/<токен>` | 97 | 100 | 100 | **63** |

Шістдесят три бали на гостьовій сторінці — не недогляд, а мета: вона закрита від пошуку (`Disallow: /s/` і `X-Robots-Tag: noindex`), і Lighthouse справедливо знімає за це весь пункт `is-crawlable`. Якщо колись SEO гостьової сторінки стане 100 — це означає, що захист зник.

Що перевірено вручну проти `vite preview` і локального стеку перед злиттям 6.1: Service Worker активується і бере сторінку під контроль; після відвідування гостьового посилання в Cache Storage немає жодної адреси з `/s/`; офлайн `/lists` відкриває оболонку, офлайн `/s/<токен>` — ні; нова збірка показує банер «Є нова версія», кнопка «Оновити» підміняє код.

Після деплою — з телефона: встановити застосунок, увімкнути режим польоту, відкрити з іконки.

## Тести парсера (pytest)

**Пін на перевірену IP** — `test_fetch_pinning.py`, мережу підміняє `MockTransport`
- Зʼєднання йде на IP, `Host` і SNI лишаються доменом; порт і IPv6 у дужках зберігаються.
- Друга відповідь DNS (уже приватна) нічого не змінює — рівно той сценарій, від якого захищає пін.
- Редирект на приватну адресу → `blocked_host`; відносний редирект розгортається від домену, а не від IP; цикл редиректів → `too_many_redirects`.
- Перша адреса не відповідає → береться друга; не відповіла жодна → `upstream_error`.
- IPv4 у списку адрес стоїть перед IPv6.

**SSRF** — `test_ssrf.py`
- `127.0.0.1`, `localhost`, `169.254.169.254`, `10/8`, `192.168/16`, `172.16/12`, `[::1]`, `0.0.0.0`, `100.64/10` (CGNAT), multicast (`224.0.0.1`, `239.255.255.250`, `ff02::1`) → `BlockedHost`.
- Схеми `file`, `ftp`, `gopher` → `BlockedHost`.
- Хост, що не резолвиться → `BlockedHost`.
- Публічний хост дозволено. Єдиний тест, якому потрібна мережа.

**Токен** — `test_auth.py`, мережу заблоковано заглушкою, налаштування підставлено (не залежить від `.env`)
- Немає заголовка, порожня схема, `Basic` → `401 missing_token`.
- Кирилиця, не-ASCII байти, не три частини, зайві символи, понад 8 КБ → `401 invalid_token`, і звернення до Supabase не відбувається (ADR-023).
- Токен правильної форми доходить до Supabase.

**Витяг даних** — `test_extract.py`
- Фікстури HTML на кожен шлях витягу: JSON-LD, microdata, OpenGraph, «нічого» (`partial: true`, назва з `<title>`).
- Розбір цін у польському, англійському й українському записі, зокрема `9,99/szt.` і `299 zł.`.
- Евристика ціни: працює без розмітки, поступається розмітці, не бере «365» з «IKEA 365+» (ADR-019).
- Рекламні параметри відкидаються, змістовні лишаються (ADR-020).
- `supabase_ready` розпізнає незаповнений шаблон.

**Сервіс задач `wishlist-jobs`** — `test_jobs.py`, мережу й базу підміняють `MockTransport`, `respx` і `FakeStore` (ADR-048)
- Наявність товару: JSON-LD `InStock` / `OutOfStock` / `Discontinued`, кілька пропозицій (хоч одна в наявності — є), microdata, `product:availability` і `og:availability`; сторінка, що мовчить, — нічого певного.
- Висновок: сторінка з ціною — `ok` з ціною й валютою; «немає в наявності» — `out` із ціною; 404 і 410 — `gone`; 403, 429, 500, 503 — нічого певного; приватна адреса (`169.254.169.254`) — нічого певного, і запит до неї **не йде**.
- Чемність: різні хости — без пауз, один хост — по черзі з паузою; межа часу відкладає решту (`deferred`).
- База: secret-ключ лише в `apikey`, без `Authorization`; запит бере лише актуальні позиції з посиланням у неархівних списках, не перевірені з потрібного моменту; запис — лише поля `link_*` за `id`; `gone` не стирає ціну з минулої перевірки; «нічого певного» пише лише час.
- Застосунок: без `Bearer` — `401`; publishable-ключ замість secret — `503 jobs_not_configured`; кінцевий перенос рядка й BOM у ключі з Secret Manager обрізаються; шаблон `<ref>` — не налаштовано; `/health` називає змінні, з якими біда, і не показує їхніх значень.
- Відкритий парсер маршруту `/jobs/check-links` не має, а його `/health` показує `secret_key_present`, щойно ключ бази туди потрапив.

**Курс НБП** — `test_rates.py`, НБП і PostgREST заступає `respx` (ADR-051)
- Розбір таблиці A: лише EUR, USD, UAH з датою таблиці; зіпсовані рядки пропускаються, незнайома відповідь — помилка розбору.
- Запис — upsert за `currency`, по рядку на валюту; НБП недоступний — нічого не пишеться й помилки немає.
- `/jobs/check-links` оновлює курс і не падає, коли НБП лежить (`"fx_rates": 0`).

**Сповіщення** — `test_notify.py`, служби push і Brevo заступає `respx`, базу — `FakeStore` (ADR-049)
- Тексти: у кожній мові ті самі ключі й ті самі підстановки; гроші й дати — «1 390 грн», «1 390,50 zł», «$1,390.50», «18 жовтня»; жодного дієслова з родом («отримав», «dostałeś»).
- Події:
  - «після свята» — з наступного дня й тиждень, не для архіву;
  - щорічне — за місяць, і в архіві теж, але не для списку, чий день попереду;
  - товар — лише в живих списках, нове посилання — новий привід;
  - ціна — те саме правило, що й мітка на картці (від 15 %, лише своя ціна, та сама валюта — позиції, а без неї списку, ADR-051);
  - посилання — дата в поясі власника.
  Надіслане й вимкнене не повторюється.
- Повідомлення: одна подія — своя назва, кілька — «Нове у твоїх списках: N»; лист екранує назви; усі посилання — у v2 (`?design=v2`), зокрема `/settings?design=v2#notifications`.
- Push:
  - відомі служби push дозволено;
  - `http`, метадані хмари, `fcm.googleapis.com.evil…`, чужий порт, логін у адресі, `localhost` — ні, і запиту немає;
  - тіло розшифровує лише браузер (перевірено розшифруванням);
  - підпис VAPID — `vapid t=…,k=…` з `aud` служби й `sub` `mailto:`;
  - 410 — `gone`, 500 — `failed`;
  - зіпсовані ключі браузера чи керівний символ в адресі — `blocked`, без запиту й без падіння.
- Brevo: `api-key` у заголовку, відправник «Wishlist», `GET /account` — `ok` / `refused`.
- Запуск:
  - один push на все й лист лише з того, що просили листом;
  - мертва підписка прибирається;
  - 22:30 у Варшаві — тиша;
  - менш ніж 3 години від минулого — чекати;
  - нікуди доставити — записано раз і не повторюється щогодини;
  - збій доставки — спроба пізніше;
  - непідтверджена пошта — без листа;
  - перевірка ключа Brevo — раз на добу;
  - `Europe/Kiev` (так досі каже Chrome в Україні) — тиша за київським часом, не за UTC;
  - розклад, що спрацював на секунди раніше за три години, не відкладає на годину;
  - зламаний власник не зупиняє решту (`errors`);
  - адреса не служби push — прибрана, подія записана як пропущена;
  - Auth не відповів — власник чекає, нічого не записано.
- База: лише дозволені таблиці й admin-запит користувача; secret-ключ лише в `apikey`; жодних `claims` і `guest_*`; з `shares` — без токена; журнал надісланого — лише для предметів цього запуску, частинами по 100; непідтверджена пошта — не адресат.
- Застосунок: `/jobs/notify` без `Bearer` — `401`; без ключів — `503 notify_not_configured`, а `/health` називає, яких саме; справжні форми ключів приймаються.
- Сумісність поза тестами: тіло push, зашифроване сервісом, розшифровано незалежною реалізацією (`http_ece` для Node), а підпис VAPID перевірено ES256 у Node crypto.

⬜ Не покрито: редирект із публічного домену на приватну IP і обрізання сторінки понад `PARSER_MAX_BYTES` — обидва шляхи потребують підміни HTTP-відповідей. Сторінка понад ліміт **не** дає `413`: вона обрізається, бо мета-теги лежать у `<head>`.

### CI

`.github/workflows/ci.yml` запускається на кожен push у `main`, на кожен pull request і вручну (Actions → CI → Run workflow). Коміти, що змінюють лише `.md`, CI не запускають.

| Задача | Що робить | Приблизно |
|---|---|---|
| `frontend` | `npm run typecheck`, `vite build` | 1 хв |
| `parser` | `pytest` | 1 хв |
| `db-e2e` | локальний Supabase на раннері → `supabase test db` → Playwright на обох профілях | 6–10 хв |

Задачі йдуть паралельно й незалежно: зламаний парсер не ховає результат pgTAP. Новий push у ту саму гілку скасовує попередній незавершений прогін.

**Секретів немає і не потрібно.** `db-e2e` піднімає Supabase у контейнерах із міграцій і `seed.sql`, входить під Анною з сіду, бойову базу не чіпає. Запускаються лише потрібні сервіси (база, Auth, PostgREST, шлюз, пошта), решта виключена через `supabase start -x`. Версія CLI закріплена та сама, що в кореневому `package-lock.json`: оновлюєш CLI локально — онови й `version` у workflow.

`VITE_PARSER_URL` у CI — вигадана адреса, тож тест «Заповнити» не пропускається, а відповідь парсера підставляє сам тест.

**Коли щось червоне:**
- Натисни на задачу — у лозі видно звичайний звіт Playwright і pgTAP; падіння Playwright також позначаються біля рядка коду у вкладці «Files changed» PR.
- Для `db-e2e` при падінні зберігається артефакт `playwright-results`: скріншоти, `error-context.md` і трейси повторних спроб (у CI кожен тест має дві повторні спроби; тест, що пройшов лише з повтору, позначається як flaky — це сигнал розібратися, а не ігнорувати).
- Відтворити локально: ті самі команди з розділів вище.

### Захист `main`

У `main` не можна пушити напряму: зміни потрапляють туди лише через pull request, коли всі три задачі CI зелені. Правило — GitHub → Settings → Rules → Rulesets, налаштування описано в DEPLOY.md, розділ 8.

Для pull request фільтр `.md` вимкнено: пропущена обовʼязкова перевірка для GitHub не рахується зеленою, і PR лише з документацією не зливався б ніколи. Push у `main` (тобто вже злитий PR) CI для документації, як і раніше, пропускає.

Vercel і Cloud Run від CI не залежать самі по собі — захищає саме правило: у `main` не потрапляє нічого, що не пройшло CI, а Vercel збирає бойову версію лише з `main`.

## Тестові дані

`supabase/seed.sql` застосовується лише до локальної бази (`npx supabase db reset`), бойову не чіпає. Склад, логіни й токени посилань — у SETUP.md, розділ 8.

Дані детерміновані: номер позиції визначає ціну, пріоритет і статус, тож кожен `db reset` дає те саме. У «Великому списку» 60 позицій, з них 8 без ціни, 6 куплених, 4 подаровані, пріоритети 15 / 30 / 15. Назви змішують кирилицю, латиницю й польські літери — для перевірки сортування за правилами мови.

Ідентифікатори сіду починаються з `5eed…` і не перетинаються з pgTAP-тестами; тести проходять як на порожній, так і на засіяній базі.
