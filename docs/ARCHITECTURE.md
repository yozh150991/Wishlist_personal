# Архітектура

## Огляд

```
┌──────────────────────────────┐        ┌─────────────────────────┐
│  Браузер (PWA)               │        │  Гість (без акаунта)    │
│  React + Vite + TS           │        │  /s/:token              │
│  Service Worker + IndexedDB  │        └───────────┬─────────────┘
└──────────┬───────────────────┘                    │
           │ supabase-js (JWT)                      │ supabase-js (anon)
           │                                        │ тільки RPC
           ▼                                        ▼
┌───────────────────────────────────────────────────────────────┐
│  Supabase                                                     │
│  ├── Auth (email+пароль, підтвердження email)                 │
│  ├── Postgres + RLS  ← головний рубіж безпеки                 │
│  └── PostgREST → RPC: get_shared_list, reserve_item, ...      │
└───────────────────────────────────────────────────────────────┘
           ▲                                        ▲
           │ HTTPS + Supabase JWT                   │ PostgREST, secret-ключ
           │                                        │ (вузько, без позначок)
┌──────────┴───────────────────┐        ┌───────────┴─────────────┐
│  parser-service (FastAPI)    │        │  wishlist-jobs          │
│  POST /parse                 │        │  POST /jobs/check-links │
│  OpenGraph / schema.org      │        │  POST /jobs/notify      │
│  SSRF-guard, кеш, таймаути   │        │  закритий, код парсера  │
│                              │        │  і його SSRF-захист     │
└──────────────────────────────┘        └───────────▲─────────────┘
     Google Cloud Run                               │ ID-токен (OIDC)
                                        Cloud Scheduler: посилання — щодня 04:15,
                                        сповіщення — щогодини
```

Назовні `wishlist-jobs` ходить ще у два місця: push — на служби push браузерів (Google, Mozilla, Apple, Microsoft), листи — у Brevo API (ADR-049).

## Межі довіри

1. **Клієнт нічому не довіряє.** Уся авторизація — у Postgres RLS. Фронтенд лише зручність.
2. **Anon-роль не має `SELECT` на таблицях.** Гість бачить дані винятково через `SECURITY DEFINER` RPC, які самі перевіряють токен, термін дії та відкликання.
3. **Парсер — окремий процес** із власним мережевим периметром. Він ходить у зовнішній інтернет, тому не має доступу до БД взагалі: повертає JSON клієнту, клієнт зберігає дані через Supabase під своїм JWT.
4. **Фонові задачі — ще один процес, закритий від інтернету** (`wishlist-jobs`, ADR-048). Лише він тримає secret-ключ Supabase, ключ Brevo й приватний ключ VAPID, і викликати його може лише Cloud Scheduler зі своїм обліковим записом. Пише вузько — поля перевірки посилань за `id` позиції, журнал надісланих сповіщень, час останнього надсилання й прибирання мертвих підписок push (ADR-049); позначок гостей не читає й не пише, токенів посилань не просить. Push шле лише на хости відомих служб push.

## Хостинг

| Частина | Де | Особливості |
|---|---|---|
| Фронтенд | Vercel, збірка з теки `app` | `vercel.json`: перезапис шляхів на `index.html`, `noindex` для `/s/*` і `/l/*`, заголовки безпеки з CSP |
| Парсер | Cloud Run, `europe-central2` (ADR-021) | масштабування до нуля, `--max-instances 2` |
| Фонові задачі `wishlist-jobs` | Cloud Run, той самий регіон (ADR-048, ADR-049) | `--no-allow-unauthenticated`, `--max-instances 1`, ключі із Secret Manager; розклад — Cloud Scheduler: перевірка посилань щодня, сповіщення щогодини |
| Supabase | Frankfurt, тариф Free | проєкт засинає після тижня бездіяльності |
| Пошта | Brevo SMTP (ADR-022) | відправник — підтверджена адреса, не домен |

Кеш відповідей, кеш токенів і обмеження частоти в парсері живуть у пам'яті процесу. На Cloud Run це означає: після простою інстанс зупиняється, і кеші зникають; при двох одночасних інстансах кожен рахує ліміт окремо, тож фактична межа — до 40 запитів на хвилину замість 20. Для особистого застосунку це прийнятно.

## Потоки

### Додавання позиції з посилання
```
Користувач вставляє URL
  → фронт: POST /parse {url}   (Authorization: Bearer <supabase JWT>)
  → парсер: перевірка форми токена → GET /auth/v1/user у Supabase (кеш 5 хв)
  → прибирання рекламних параметрів → кеш відповідей (15 хв)
  → GET потоком на перевірену IP, з Host і SNI справжнього домену
    (понад 5 МБ обрізається, таймаут 8 с, до 5 редиректів,
    кожна адреса й кожен редирект проходять SSRF-перевірку)
  → витяг og:title / og:image / product:price / schema.org Offer
  → {title, price, currency, image_url, site_name} або часткові дані
  → фронт заповнює форму, користувач редагує і зберігає
  → supabase.from('items').insert(...)
```
Якщо парсер недоступний або нічого не знайшов — форма відкривається з підставленим URL і порожніми полями. Додавання ніколи не блокується.

### Створення спільного посилання
```
Вибір позицій (чекбокси) → «Поділитися»
  → rpc('create_share', {list_id, item_ids, title, hide_prices, ...,
                         expires_on: '2026-12-20', expires_tz: зона браузера})
      база: expires_at = 23:59:59 того дня за expires_tz (ADR-037)
      bad_time_zone → повтор із p_expires_at (кінець дня за годинником пристрою, без зони)
  → повертає share з token
  → фронт формує https://<host>/s/<token>
```
Термін — доба **власника**: зону дає його браузер (`lib/zones.ts`, `deviceTimeZone`), момент рахує база. Гість бачить «Діє до 20 грудня, 23:59 за Києвом» — годинником власника, бо саме тоді посилання згасне для всіх. Для кількох міст, де живе більшість власників, назва у відмінку — з i18n (`zone.*`); для решти — назва зони від `Intl` у дужках. Сторінка «Мої посилання» показує день у зоні посилання: власник у відрядженні бачить той самий «20 грудня».

### Перегляд гостем (ADR-035)
```
GET /s/:token[/g/:key]            (гостьова v2 — /l/:token[/g/:key], той самий потік, ADR-041)
  → ключ з адреси лягає в localStorage (wl.gk.<token>), адреса стає /s/:token (чи /l/:token)
  → rpc('get_shared_list', {token, key})   [anon]  → позиції, taken_qty, mine_qty, код
  → rpc('register_share_view', {token})
  → «Я візьму це»: ключ генерується й зберігається ДО запиту
      → rpc('claim_item', {token, item_id, key, quantity})
  → «Звільнити»: rpc('release_claim', {token, item_id, key})
  → «У мене вже щось відкладено»: rpc('redeem_guest_code', {token, code}) → новий ключ
```
Ключ гостя — носій права на свої позначки в одному списку, не особа: сервер зберігає лише `sha256(list_id:ключ)`. Джерел два — особисте посилання, яке гість надсилає собі («Забери доступ із собою»), і `localStorage` цього браузера; третій шлях — короткий код, що видає новий ключ тієї самої ідентичності. Старий ключ браузера до ADR-035 (`wl.guest`, один на всі списки) підхоплюється лише там, де з ним уже є позначки.

Гість типово бачить **вільні** (і свої) — прийшов вибирати, а не читати каталог; «Усі» поруч. Програш гонки пояснюється на місці позиції (`role="status"`), кнопка зникає, а не блокується. Коли вільного не лишилось — «Усе вже розібрали» з «Стежити за списком»: знімок позицій живе в `localStorage` (`wl.watch.<token>`), наступного разу сторінка показує, що звільнилось. Пошту не просимо.

Власник бачить на своїй позиції «Скинути позицію» (діалог позиції) — `rpc('release_item_claims')`, яке нічого не повертає. Кнопка є завжди й однаково: інакше сама її поява була б індикатором.

### Розділи й ручний порядок (ADR-036)
```
Сторінка списку
  → fetchList (з кількістю позицій) ∥ fetchSections ∥ перша партія позицій
  → ≥ 12 позицій або є розділ → режим «Розділи»: useItems(…, 'all') — список цілим
    (перша партія не показується — useItems знає, яким способом завантажено),
    фільтри на клієнті (matchesQuery), групи groupItems → SectionsView
  → інакше плаский список, як був: keyset-пагінація list_items_page
  → перетягування за ручку (@dnd-kit) → оптимістично на екрані → rpc('reorder_items' | 'reorder_sections')
  → «За пріоритетом» / «За ціною» — плаский список, лише вигляд власника
Гостьова: get_shared_list віддає позиції вже в ручному порядку й розділи зі спільними позиціями;
  гість фільтрує «Вільні · Усі», порогом ціни з терцилів і «Високий» на клієнті
```

### Підсумки після події (етап 6.2)
```
Сторінка списку, у списку є event_date
  → дата минула (порівнюються календарні дні за годинником пристрою — банер бачить
    лише власник, тож це й є його доба, як і в терміні посилання) і active_count > 0
  → EventSummary показує нагадування
     ├── «Пізніше» → localStorage: {список: дата}; нагадування зникає до зміни дати
     └── «Підбити підсумки» → фільтр statuses=['active'], режим вибору,
                              усі показані позиції вибрано
       → масова зміна статусу (gifted / purchased) — той самий шлях, що й вручну
  → active_count = 0 → замість нагадування тихий рядок «Подія минула · подаровано N з M»
```
Окремих запитів і колонок режим не додає: рахує `list_totals`, статуси міняє наявна масова дія. Дата події лишається в `lists.event_date` — вона й раніше зберігалась саме для цього (DATA_MODEL).

Відмова живе в `localStorage` разом із датою, а не прапорцем: подію перенесли на наступний рік — нагадування зʼявиться знову. Ключ — `wl.summaryDismissed`; у приватному режимі браузера запис може не вдатись, і тоді нагадування просто повернеться наступного разу.

### Експорт та імпорт (етап 6.3)
```
Сторінка списку → «Експорт»
  → fetchAllItems(listId)        # діапазонами по 1000: стільки ж у max_rows PostgREST
  → toCsv(items) | toJson(list, items)
  → downloadText() — Blob і <a download>

Сторінка списків → «Імпорт» → файл
  → parseFile() — формат за розширенням, а без нього за вмістом
  → перевірка кожного значення за межами зі схеми
  → попередній перегляд: що буде створено + зауваження по рядках
  → createListWithItems() — новий список, позиції партіями по 100
```
Файл описує вміст, а не рядки бази: ні `id`, ні `owner_id`, ні `created_at`. **Ні броней, ні токенів спільних посилань** — власник не бачить броней ніде, і вивантаження не стає обхідним шляхом (CLAUDE.md §3.2, §3.5). Побічний наслідок: файл можна внести в інший акаунт.

Правила формату живуть у `lib/transfer.ts` без React, мережі й DOM — тому перевіряються тестами без браузера. Робота з файлом винесена окремо в `lib/download.ts`.

**«Мої дані» (v2, Налаштування).** Усі списки з позиціями й опис посилань одним файлом `wishlist-РРРР-ММ-ДД.json`, формат `wishlist-personal-account` (`toAccountJson` з `lib/transfer.ts`). Кожен запис у `lists` — ті самі `list` і `items`, що й у файлі одного списку, тож будь-який список звідти можна внести імпортом. Посилання описані назвою, списком, датами, переглядами й кількістю позицій — **без токенів**: адреса посилання — ключ до гостьової сторінки, а файл живе далі без застосунку. Позначок немає тим паче. Хід видно — «Експортую… 3 з 12», — і його можна скасувати.

Імпорт завжди створює **новий** список і ніколи не змінює наявний (ADR-027). Непридатні рядки не зупиняють файл: рядок без назви пропускається, а виправні дрібниці (невідомий статус, ціна з комою) виправляються — і те, і те видно в попередньому перегляді до створення.

### Перевірка посилань (ADR-048)
```
Cloud Scheduler, щодня 04:15 за Варшавою
  → POST /jobs/check-links у wishlist-jobs   (ID-токен облікового запису wishlist-scheduler)
  → Cloud Run пропускає лише власника ролі run.invoker; застосунок — лише з Bearer
  → GET /rest/v1/items                        (apikey: sb_secret_…, без Authorization)
      актуальні, з посиланням, у неархівних списках, не перевірені понад 20 год,
      найдавніші першими, партіями по 50, поки є черга й час
  → групи за хостом: кілька хостів одночасно, в одному — по черзі з паузою 2 с
  → fetch_html — той самий SSRF-захищений завантажувач, що й у парсері
      404 / 410                     → gone
      schema.org «немає в наявності» → out   (+ ціна й валюта зі сторінки)
      сторінка є                     → ok    (+ ціна й валюта зі сторінки)
      антибот, 5xx, тайм-аут, блок   → нічого певного: лише link_checked_at
  → PATCH /rest/v1/items?id=eq.<id>          лише link_* поля
  → понад 300 с — решта лишається на завтра; у лог — лише лічильники
```
Сервіс нічого не знає про позначки гостей і нічого не міняє в тому, що бачить гість: гостьові RPC полів `link_*` не віддають. Ціну в списку він теж не чіпає — лише запам'ятовує, що побачив у магазині; рішення за власником (v2, діалог позиції). Нове посилання скидає висновок тригером `items_link_reset`, тож заміна посилання у v1, яка про перевірку не знає, теж дає чесне «ще не перевірено».

Код задач — `services/parser/app/jobs_*.py`: налаштування (`jobs_config.py`), доступ до бази (`jobs_store.py`), сама перевірка (`jobs_links.py`), сповіщення (`jobs_notify.py`, `jobs_push.py`, `jobs_mail.py`, `jobs_texts.py`), застосунок (`jobs_main.py`). Образ той самий, що й у парсера; який застосунок запускати, каже змінна `APP_MODULE`. Відкритий парсер (`app.main`) модулів задач не імпортує.

### Сповіщення власника (ADR-049)
```
Налаштування v2 → «Сповіщення» (або аркуш «Поділитися» після посилання)
  → «Увімкнути сповіщення»: системний запит дозволу лише за натиском
  → pushManager.subscribe(ключ VAPID) → rpc('save_push_subscription')   пристрій — тому, хто ввімкнув останнім
  → notification_settings: подія × канал, пояс браузера

Cloud Scheduler, щогодини :05 → POST /jobs/notify у wishlist-jobs
  → власники, у кого хоч щось увімкнено
  → 22:00–9:00 за їхнім поясом — чекаємо; надсилали менш ніж 3 год тому — чекаємо
  → списки, позиції (статус перевірки), посилання, що згаснуть за 3 дні
  → події after_event / yearly / link / price / share, яких ще немає в notification_log
  → push: один на все, зашифрований для кожного пристрою (aes128gcm, VAPID) → служба push браузера
     404/410 — підписки немає, рядок прибрати
  → лист: один на все, Brevo API, лише на підтверджену пошту, мовою user_metadata.locale
  → notification_log і last_sent_at; у лог — лише лічильники
```
Service Worker показує push через `push-sw.js` (підключений `workbox.importScripts`): заголовок, текст і відносна адреса всередині застосунку. Натиск фокусує відкриту вкладку й веде туди, або відкриває нову. Чужих доменів із push не відкриває.

Вихід з акаунта знімає підписку цього пристрою (`forgetPushOnThisDevice` у `lib/auth.tsx`): поки сесія жива — ще й рядок на сервері (`forget_push_subscription`). Наступна людина за пристроєм не отримає сповіщень із назвами чужих списків. Адреса підписки йде лише в тілі запитів, ніколи — фільтром у рядку адреси.

Посилання з push і листів несуть `?design=v2`: сповіщення — функція v2, а вибір версії живе в браузері. Системний запит дозволу й підписка обмежені тайм-аутами (60 і 20 с): тихий запит Chrome може не відповісти ніколи.

## PWA і офлайн-режим

### Зроблено (етап 6.1, ADR-025)

- **Встановлення.** `vite-plugin-pwa` генерує `manifest.webmanifest` (`start_url: /lists`, `display: standalone`) та Service Worker. Іконки — `public/icons/`, PNG генеруються з SVG скриптом `scripts/generate-icons.mjs`. У налаштуваннях розділ «Застосунок на телефоні»: кнопка встановлення там, де браузер надсилає `beforeinstallprompt` (`lib/install.ts`), інструкція для iPhone і iPad, де такої події немає.
- **Оболонка офлайн.** Service Worker заздалегідь кешує збірку: код, стилі, шрифти (кирилиця й латиниця; грецькі й вʼєтнамські підмножини виключено), іконки — близько 770 КБ. Будь-яка адреса застосунку відкривається з кешованого `index.html` і без мережі.
- **Гостьові сторінки не кешуються.** `/s/*` і `/l/*` виключено з навігації Service Worker: відповідь із токеном (і ключем гостя) в адресі не лягає в кеш пристрою. Перевіряється після збірки `npm run check:pwa`, і в CI теж.
- **Дані не кешуються.** Запити до Supabase і парсера завжди йдуть у мережу. Без мережі сторінки показують «Немає зʼєднання» (`lib/errors.ts`), а не порожній стан. Запити `/rest/v1/` при `navigator.onLine === false` відхиляються одразу, без трьох повторів клієнта PostgREST (`lib/supabase.ts`). Запити автентифікації за станом мережі не відхиляються — невдале оновлення токена клієнт Auth може сприйняти як привід завершити сесію, — але обмежені тайм-аутом 15 с: сервер, що прийняв зʼєднання й замовк, інакше лишав би форму входу з вимкненою кнопкою назавжди. Обрив за тайм-аутом клієнт бачить як `AuthRetryableFetchError`, тож сесія від нього не завершується, а `authErrorKey` показує «Сервер не відповідає».
- **Читання офлайн (етап 6.4).** Успішне завантаження сторінки списків і першої партії позицій лишає знімок в IndexedDB (`lib/cache.ts`). Коли мережі немає, замість «Немає зʼєднання» показується цей знімок із позначкою, коли його збережено (`Banners`, стан `stale`). Кожен запис підписаний `userId`: чужий підпис — промах, а вихід з акаунта стирає базу цілком. Запис знімка перевіряє, що його `userId` досі той, хто увійшов (`setCacheOwner` з `lib/auth.tsx`): інакше запит, що вийшов до виходу й повернувся після стирання, поклав би знімок назад. У кеш не потрапляють ні токени спільних посилань, ні сторінка `/shares`, ні броні, ні вибірки з пошуком чи фільтрами (ADR-028).
- **Черга змін (етап 6.5).** Зміна позиції, яка не дійшла **через мережу**, лягає в чергу (`lib/outbox.ts`) і одразу застосовується до екрана й до знімка в кеші — тією самою чистою функцією `applyToItems` (`lib/outboxOps.ts`). Відмова сервера в чергу не потрапляє: людина бачить помилку негайно. Черга відправляється сама при події `online` і при відкритті застосунку, по порядку; мережевий збій зупиняє відправку, відмова сервера викидає зміну з черги з поясненням. Ідемпотентність: `id` нової позиції генерує клієнт, тож повтор упирається в первинний ключ. Офлайн працюють лише позиції в наявному списку — не створення списків, не посилання, не імпорт (ADR-029). Відправляє чергу хук `useOutbox` (`lib/useOutbox.ts`), спільний для обох версій: у v1 його стан показує `Banners`, у v2 — рядок над екраном у `ShellV2`. До кроку 3в v2 чергу не відправляла зовсім — зміни, зроблені без мережі у v2, чекали переходу у v1.
- **Оновлення.** Нова збірка не підміняє відкриту сторінку сама: `UpdatePrompt` показує банер, оновлення — за кнопкою. Відкритий застосунок перевіряє оновлення щогодини. У режимі розробки Service Worker вимкнено.
- **Колір системних панелей** (`theme-color`) збігається з верхньою панеллю застосунку і змінюється разом із темою.
- **Push (ADR-049).** `public/push-sw.js` підключається до згенерованого Service Worker через `workbox.importScripts`: показує сповіщення й веде натиском у застосунок. `npm run check:pwa` падає, якщо підключення чи обробники зникнуть.

## Стан на клієнті

Три провайдери, вкладені саме в цьому порядку:

```
ThemeProvider        тема, схема, контраст, поверхня → resolveAppearance(); до першого
                     рендера атрибути ставить скрипт у <head>
└── I18nProvider     мова; визначається з localStorage → navigator.languages → uk
    └── BrowserRouter
        └── AuthProvider   сесія Supabase; усередині роутера, бо потребує навігації
            └── LocaleSync мову інтерфейсу → user_metadata.locale, для листів (ADR-024)
```

Зовнішніх бібліотек стану немає — контексту достатньо. Дані позицій живуть у власному хуку `useItems` над supabase-js, без React Query: офлайн-черга з етапу 6 усе одно вимагатиме власного шару.

## Стилі

Без CSS-фреймворку (ADR-015, уточнено ADR-031).

Кольори живуть окремо від решти стилів — у `src/styles/tokens.css`. Там **дванадцять повних наборів**: п'ять схем смаку (Шавлія, Слива, Полотно, Цитрус, Ніч) і Вугіль × дві теми. Схема, тема, оформлення списку й версія дизайну ставляться атрибутами на `<html>`:

```
<html data-scheme="sage" data-theme="light" data-appearance="358" data-design="v1">
```

**Що стане атрибутами, вирішує одна функція** — `resolveAppearance()` у `lib/appearance.ts` (ADR-033). Викликається вона рівно в одному місці, у `ThemeProvider`, і діє за правилом «перший спрацьований виграє»:

1. висока контрастність глядача (тумблер або системне `prefers-contrast: more`) → Вугіль, оформлення не застосовується;
2. свої екрани власника → його схема з профілю, без оформлення;
3. гостьова → схема власника + оформлення списку;
4. тема — завжди глядача, у будь-якій ролі.

**Оформлення списку** (ADR-034) — не набір у `tokens.css`, а змінні акцентної рампи, пораховані з одного відтінку генератором `lib/hue-ramp.js` і поставлені інлайном на `<html>` поверх набору. Оформлень може бути скільки завгодно, а наборів лишається дванадцять; той самий генератор імпортує `check:contrast`. Лягає лише на гостьову й на превʼю «Показати, як бачить гість»; на своїх екранах власника його немає.

Поверхню (свої екрани / гостьова / превʼю гостьової) каже сторінка хуком `useSurface()`; пішла зі сторінки — застосунок повертається до своїх екранів. Атрибути до першого рендера пише інлайновий скрипт у `<head>` — скорочене правило 1–2, без оформлення, — інакше на холодному старті блимає чужа палітра. Жоден компонент не знає, яка схема активна, і ніде не звіряє її ім'я. Перемикання миттєве: на два кадри `ThemeProvider` вимикає всі `transition`, щоб кольори не перетікали.

**Склад палітри повний або ніякий.** Пропущений токен не ламає сторінку: він тихо падає на `:root`, тобто на світлу Шавлію, і в темній схемі дає світлий значок на темній картці. Тому кожен набір оголошує всі 45 змінних, навіть ті, якими сьогодні ніхто не користується.

`src/styles.css` — усе решта: ритм (4/6/8/10/12/16/24/32), радіуси, тіні, типографіка й компоненти. Літеральних кольорів у ньому немає й бути не може: `npm run check:contrast` падає на будь-якому hex у `src/` (`.css`, `.ts`, `.tsx`), крім `tokens.css`.

Вибір власника — тема, схема й висока контрастність — їде в `profiles.theme` / `profiles.scheme` / `profiles.high_contrast`, щоб переїжджав між пристроями; `localStorage` лишається, бо інлайновому скрипту треба щось прочитати до того, як приїде профіль. **Гість схеми не обирає**: він бачить схему власника, а «для себе» має лише тему й високу контрастність, які живуть у його браузері й на сервер не їдуть. Доступність від цього не страждає — правило 1 віддає йому Вугіль незалежно від будь-якої схеми.

### Версія дизайну (ADR-032, ADR-039)

Третя вісь стоїть **над** двома попередніми: v2 — це інші екрани, інший порядок кроків, новий вхід і нова функціональність, а не перефарбована v1. Тому розділення проходить по таблиці маршрутів, а не всередині компонентів:

```
src/
  App.tsx                     провайдери, сесія, мова — спільне для обох версій;
                              гостьові маршрути /s/… і /l/… — тут, вище за вибір версії
  designs/
    DesignRoutes.tsx          вибір таблиці; v2 одразу (усталена, ADR-052), v1 ліниво; GuestV2Screen для /l/…
    v1/RoutesV1.tsx           маршрути v1 -> наявні routes/ і components/
    v2/RoutesV2.tsx           маршрути v2
    v2/screens/               екрани v2; GuestV2.tsx — гостьова під /l/…
    v2/v2.css                 стилі форми v2 — імпортують модулі v2; з ADR-052 у головному пакеті
  lib/                        спільне для обох версій, не дублюється
```

Екрани v1 лишилися там, де були: переїзд у `designs/v1/` перейменував би півсотні імпортів заради нічого. Коли v1 піде на спокій, `routes/`, `components/` і її таблиця зникнуть разом.

**Спільне — усе, що не екран.** `lib/` (Supabase, автентифікація, вигляд, офлайн-кеш, черга змін, парсер, експорт) в однині: інакше кожне виправлення двічі, а інваріанти приватності (CLAUDE.md §3) розходяться між версіями непомітно. Новий запит з'являється в `lib/` і доступний обом версіям. Нова операція офлайн-черги — теж у `lib/`: після перемикання на v1 черга не має застрягти на операції, якої v1 не знає.

**`data-design` показує версію екрана, а не вибір у сховищі.** Інлайновий скрипт у `<head>` ставить його так: адреса `/s/…` → v1, `/l/…` → v2, усе інше → `wl.design`, а без нього — v2 (усталена з ADR-052). Після старту те саме правило тримає `ThemeProvider`: верхня таблиця маршрутів в `App.tsx` при кожному переході передає йому версію адреси (`useRouteDesign(designOfPath(pathname))`), і вона перемагає вибір. Без цього React затирав би атрибут, який поставив скрипт. `useDesign()` і далі повертає вибір людини — за ним `DesignRoutes` обирає таблицю для решти адрес.

**Виходів із v2 два.** Кнопка на її екрані — і адреса `?design=v1`, яку читає інлайновий скрипт у `<head>` ще до React, тобто вона працює й тоді, коли v2 падає на першому рендері. Параметр одразу знімається з адреси й не чіпає решту параметрів. Саме перемикання — перехід на корінь із перезавантаженням: сторінки, на якій стоїть людина, в іншій версії може не бути.

**До входу версію обирають на самому екрані входу**: на входах і реєстрації обох версій є текстовий перемикач. Адреси повернення з листів і OAuth несуть `?design=<поточна>`, тож лист, відкритий на іншому пристрої, потрапляє в ту версію, з якої його замовили. Маршрути повернення є в обох таблицях. Шаблони листів Supabase одні на обидві версії й містять лише посилання: кодів із пошти для входу чи підтвердження акаунта немає ні в v1, ні в v2 (ADR-042).

**Гостьову версію визначає форма посилання.** `/s/:token` і `/s/:token/g/:key` — гостьова v1, `/l/:token` і `/l/:token/g/:key` — гостьова v2 (ADR-041). Токен той самий, ключ гостя — теж: зберігається `sha256(list_id:ключ)`, тож особисте посилання працює під обома префіксами. Вибір власника на гостьову не впливає: у гостя немає його сховища. Поки гостьова v2 не готова, «Мої посилання» в обох версіях копіюють `/s/`. Коли v1 піде, `/s/…` рендеритиме гостьову v2 — роздані посилання не вмирають.

**Гостьова v2 (крок 5а, ADR-053).** Під `/l/…` — власні екрани: `designs/v2/screens/GuestV2.tsx` (сторінка) і `GuestPartsV2.tsx` (картка й аркуші). Дані — `get_guest_list` і `claim_item_v2` з `lib/shares.ts`: обгортки над замороженими `get_shared_list` і `claim_item`, що додають лише підпис гостя (ADR-053, п. 3); «Зняти», код і «Стежити» — ті самі `release_claim`, `redeem_guest_code`, `register_share_view` і `lib/guest.ts`, що в v1. Згори вниз: шапка-листівка на `--color-guest-header` (дата, «Мої броні · N» або «Уже маю броні», назва, кількість, повідомлення, термін) → «Вільні / Усі», поріг ціни з даних, «Дуже хочу» й «Вільних N з M · на …» → «Схоже за ціною» після програної гонки → розділи з картками → примітка, що власник нічого не бачить, і підвал «Вигляд» + мова. Картка має три стани (`data-state`): вільна — «Беру»; своя — контур акценту, «Ви берете», «Зняти» (і «Беру ще» для кількох штук); чужа — «Уже взяли», без дії. «Беру» відкриває `BookSheetV2`: «Берете …?», скільки (для кількох штук), необовʼязковий підпис, підставлений з минулої броні; той самий аркуш показує код після першої броні й гілку «встигли раніше». «Зняти» — тост на 6 с, запит `release_claim` після відліку (`useUndo`). Ключ з особистого посилання прибирається з адреси на той самий префікс `/l`. Мертве посилання — один екран із долею броней (потік G). Посилання для гостей «Мої посилання» видають `/s/…` до кроку 5г. Код v2 більше не бере екранів v1.

**Гостьові листи (крок 5б-1, ADR-054).** В аркуші броні — необовʼязкова пошта; «Уже маю броні» має режим «Надіслати код на пошту» (`send_guest_code`, відповідь однакова, є адреса чи ні). Бронь із поштою й «код на пошту» кладуть рядок у `guest_mail`; тригер через `pg_net` будить відкритий сервіс `wishlist-guestmail` (`services/parser/app/mail_main.py` + `guest_mail.py`), той читає чергу secret-ключем і шле через Brevo тим самим `Mailer`, що й сповіщення власника. `pg_cron` раз на 10 хвилин будить його ще раз. Відписка з листа — `/l/{токен}/u/{mail_token}`: `GuestV2` одразу кличе `guest_mail_set(…, false)`, прибирає секрет з адреси (у стан історії вкладки) і показує «Повернути листи».

```
гість «Беру» з поштою ──► claim_item_v2 ──► claims + guest_mail ─┐
                                                                  │ тригер, після коміту
                              pg_cron */10 ──► wake_guest_mail ◄──┘
                                                     │ net.http_post (секрет із Vault, без даних)
                                                     ▼
                                   wishlist-guestmail POST /wake
                                                     │ читає guest_mail + ідентичність + посилання
                                                     ▼
                                              Brevo ──► лист гостю
```

**Дані — спершу розширити, потім прибрати.** Міграції додаткові, кожна нова колонка має усталене значення, що дорівнює поведінці v1. Нова поведінка вмикається лише налаштуванням з інтерфейсу v2, тож список, який ведуть у v1, поводиться як раніше, і сервер ніде не перевіряє версію. RPC v1 заморожені, у v2 — власні. Позначки — одна таблиця `claims` на обидві гостьові. Чернетки без назви не повертаються ні з RPC v1, ні з гостьових. Те, що v1 уже має в базі (схеми й контрастність, оформлення списку, ключ гостя, розділи, термін посилання — ADR-033…037), v2 отримує готовим.

**Стилі.** Палітра спільна: v2 бере ті самі дванадцять наборів із `tokens.css`, ту саму `resolveAppearance()` і ті самі поля профілю, що й v1 (ADR-033, ADR-034); власних токенів у неї немає, і `check:contrast` читає один файл, як і раніше. Форма своя: стилі v2 — `designs/v2/v2.css`, класи з префіксом `v2-`; файл імпортують `RoutesV2.tsx` і `GuestV2.tsx`, тож він їде в лінивий чанк, і користувач v1 його не завантажує. Класів v1 стилі v2 не перевизначають. Ранній `styles/design-v2.css` — шар перевизначень над v1 — видалено разом з імпортом у `main.tsx`. Гарнітури в обох версіях однакові — Rubik і Manrope.

**Вхід v2 (крок 2, потоки A, Q, T; ADR-042).** Екрани свої — `LoginV2`, `RegisterV2`, `ResetV2`, `NewPasswordV2` у `designs/v2/screens/`, з частинами в `AuthPartsV2.tsx`. Логіка, яка не є розміткою, — у `lib/`, бо листи, Redirect URLs і Google в обох версій одні:

- `lib/authFlow.ts` — адреса повернення з `?design=` (`authReturn`), вхід через Google, розбір помилок, які Supabase дописує до адреси повернення (`readRedirectError`: скасовано / протерміновано / інше), пошта на наступний крок у `localStorage` (`wl.authEmail`, стирається після входу), «Відкрити пошту» для відомих поштових сервісів, посилання на той самий екран в іншій версії (`designSwitchHref`).
- `lib/password.ts` — вимоги до пароля: щонайменше 8 символів, не збігається з поштою, не з короткого переліку найпоширеніших. Це підказка, не захист: остаточне слово за Supabase.

Поведінка, яку легко зламати: валідація пошти — на виході з поля, «порожньо» — лише після натиску; кнопка ніколи не блокується, натиск веде фокус до першого хибного поля; поля не очищаються; понад 8 с очікування — «Скасувати» (запит, що запізнився, ігнорується). Після трьох невдалих спроб поспіль — пауза на 30 с із лічильником на кнопці й посиланням на скидання пароля: це підказка людині, а не захист, його дає rate limit Supabase.

Лист підтвердження з v2 веде на `/login?design=v2&from=confirm`: у тому ж браузері PKCE створює сесію й екран входу одразу веде далі, в іншому — сесії немає, і екран каже «Пошту підтверджено, увійди паролем». Протерміноване посилання — сторінка «Посилання вже не діє» з повторним листом. Вхід із непідтвердженою поштою — «Спершу підтверди пошту» з тим самим повторним листом: у застосунок пускає лише підтверджена пошта (ADR-043). «Новий пароль» без сесії — «Це посилання вже використане» з полем пошти. Після нового пароля інші пристрої виходять з акаунта (`signOut({ scope: 'others' })`).

Google — за змінною `VITE_AUTH_GOOGLE=1`, лише коли провайдер налаштований у Supabase (DEPLOY.md, 4.1). Кнопка — текстова, без логотипа. Скасоване вікно Google повертає на той самий екран без червоного.

**Каркас і «Мої списки» v2 (крок 3а, потоки U, B, A4).** `ShellV2.tsx` — захист маршрутів (`RequireAuthV2`: поки сесія перевіряється — тиха заглушка, без сесії — `/login?next=…`) і каркас: навігація внизу на телефоні, бічна колонка 232 px від 56rem з рядком «Акаунт» і виходом. Навігація одна, підпис вибирає `useMediaQuery`. Вихід (`SignOutV2`) спершу питає, якщо в офлайн-черзі лишились зміни.

`ListsV2` — головна: «Найближчі» (за датою, списки без дати одразу за ними) і «Минулі». Рядок картки — «18 жовтня · через 21 день» (`Intl.RelativeTimeFormat`), «без дати · 6 позицій», «1 січня · 4 позиції не розібрані»; множина — `Intl.PluralRules` з окремим ключем на кожну форму (`useCounts`). «Не розібрано» — статуси самого власника: дані дає `fetchListsOverview()` у `lib/db.ts` (два агрегати одного вкладення, фільтр на псевдонімі; якщо сервер такого не прийме — запасний `fetchLists()` без цього числа). Про позначки гостей на головній нічого (ADR-040). Коло картки — відтінок оформлення списку, якщо воно діє й не ввімкнено високу контрастність, інакше тон блоку. Порожня головна — шаблони свят, які лише підставляють назву. Без мережі — збережена копія з `lib/cache.ts` під тим самим ключем, що й у v1. «Вітаю!» — 4 с і лише після входу з екрана входу.

`NewListV2` — новий список однією назвою (решта — усередині списку), дата необов'язкова, валюта — з `profiles.default_currency`, інакше PLN. Дубль назви й минула дата — попередження теракотою, не заборона. Чернетка — у `localStorage` (`wl.v2.listDraft`); «Назад» із вписаним питає «Лишити чернетку?», порожню форму закриває мовчки. Збережений список одразу відкривається: перша позиція додається всередині. Тип події, «щороку» й архів — крок 4: для них потрібні нові поля.

**Сторінка списку v2 (крок 3б-1, потоки C, F, O, R, V).** `ListV2` — згори вниз: назва й «6 позицій · 19 жовтня» → сума актуального («12 659 грн» і «у 5 актуальних позиціях · 1 без ціни · 1 подаровано») → пошук, сортування, «Фільтри» (статус, ціна «від–до») і чипи «Усі / Без ціни» — щойно є хоч одна позиція (ADR-050; у пакеті — від 20) → позиції → «Куплене й подароване», згорнуте, поки є актуальне. Увімкнені фільтри аркуша — чипи з «×» під пошуком; фільтри не запамʼятовуються. «Експортувати список» у меню списку пише ті самі CSV/JSON, що v1 (`lib/transfer.ts`), з позицій на сторінці. «Імпорт із файлу» на «Моїх списках» — `ImportSheetV2` з тим самим `parseFile`, що в v1, і `createListWithItems`; опис і дату з JSON переносить.

Список вантажиться цілим (`useItems(…, 'all')`), а сортування, групи, фільтр і підсумок рахуються на клієнті чистими функціями `lib/itemsView.ts` (гроші — у мінорних одиницях). Так зміна, що лягла в офлайн-чергу, одразу видна й у сумі, й у правильній групі. Сортування — лише вигляд власника й пам'ятається для кожного списку (`localStorage`, `wl.v2.sort.<id>`): «Вручну» (порядок гостя, з розділами, якщо вони є), «Пріоритет» (заголовки «Дуже хочу · 5», «Було б добре · 11», «Просто ідея»), ціна в обидва боки (без ціни — у кінці), «Нещодавно додані». Порожній пошук — «Нічого за «…»» з тим, що ще звужує, і двома ходами: «Скинути фільтри» чи «Додати як нову позицію». Про позначки гостей на сторінці нічого — ні на картці, ні в підсумку, ні фільтра «вільні» (ADR-040).

Зміни позицій — через офлайн-чергу `run()` з `lib/outbox.ts`. Створення й зміна спершу йдуть на сервер (відмову показує форма), потім застосовуються до екрана; дійшло — ще й тихе перечитування `refresh()` з `useItems`, без скелета. Статус із меню «⋯» — одразу на екрані, відмова сервера повертає як було. Видалення — тостом «Відмінити» на 6 с (`useUndo` з `lib/undo.ts`, спільний із v1): позиція ховається одразу, а запит іде, коли відлік скінчився, тож відкат миттєвий і не знімає позначок гостей, які зникли б каскадом разом із позицією (ADR-044). Сервер відмовив — позиція повертається з поясненням у рядку картки й «Ще раз». Щойно додана позиція підсвічена 2 с, а її тост «Відмінити» просто видаляє її: вона ще не потрапила в жодне посилання.

**«Вибрати кілька» (паритет із v1).** Пункт меню списку вмикає режим вибору: картка стає прапорцем (`ItemCardV2` з `select`), «⋯», свайп, «+» і картка «Після свята» ховаються, «Куплене й подароване» розгортається. Панель унизу (`.v2-selbar`, на місці тосту) — «Вибрати всі показані» з урахуванням пошуку й фільтрів, «Статус», «Поділитися», «Видалити». Статус вибраних — одна операція `status` черги з усіма id: оборотна, тож без підтвердження, працює й офлайн. Видалення — одна операція `delete` після `ConfirmSheetV2`, без відліку: діалог для масового видалення передбачає `lib/undo.ts`, а текст підтвердження каже, що позиції зникнуть і з посилань. «Поділитися» відкриває `ShareSheetV2` з `preselect` — лише актуальні вибрані без чернеток; решту можна додати в «Обрати». Після дії режим закривається, а що зроблено — рядком згори.

`ItemSheetV2` — нова позиція й зміна позиції: на телефоні на весь екран із «Скасувати · Нова позиція · Додати» вгорі, на десктопі — вікно по центру; клік повз вікно форму не закриває. Нова починається з посилання: поле, «Вставити з буфера» (буфер читається лише на натиск — вебсторінка не бачить його без дозволу), «або», «Вписати вручну». Вставлене посилання одразу читається парсером, але поля вже живі, і вписане людиною парсер не перетирає; збій лишає посилання в записі й дає ручну форму з теплою приміткою. Хибний формат — підказка під полем і «Додати без посилання» (R1). Те саме посилання, що вже є в списку (без рекламних міток, `www.` і кінцевої `/`), — «Ця річ уже в списку» з «Кількість: 2» і «Відкрити наявну» (R2); схожа назва — тихий рядок під полем. Ознаки — на вимогу, «+ Розмір, колір» (V1): порожній рядок не зберігається. Своє фото — пізніше; поки лише фото з магазину, яке можна прибрати. У зміні позиції внизу — сліпе «Скинути позицію» (ADR-035).

Розділи (ADR-036): створення — з меню списку, перейменування й видалення — з «⋯» біля заголовка розділу.

**Дії зі списком (крок 3б-2, потоки D, F, H, Q2, V3, W1).** Меню «⋯» у шапці: «Поділитися» (вона ж — іконка в шапці), «Показати, як бачить гість», «Змінити порядок», «Оформлення списку», «Новий розділ», «Налаштування списку». Експорт у файл поки лише в v1 — внизу меню посилання на той самий список там.

- `ShareSheetV2` — «Поділитися»: заголовок, повідомлення, «Показувати ціни», «Гості можуть позначати, що беруть», «Діє до» й «Що побачать гості · 13 з 15» (усталено — усі актуальні позиції в порядку гостя). На телефоні вибір позицій і «Переглянути як гість» — окремі кроки, на десктопі — поруч із живим превʼю (H). Рядок «Приховано для цього посилання: N позицій» ловить «випадково поширив дороге». Посилання створює той самий `createShare` з `lib/shares.ts`, копіює в буфер само, а якщо браузер не дав — лишаються «Копіювати» й системне «Поділитися». «Відкликати доступ» — одразу там же, з підтвердженням. Посилання поки `/s/…`, як і в «Моїх посиланнях».
- `PreviewV2` — превʼю гостя: гостьові токени, поверх — оформлення списку, якщо воно діє (висока контрастність вимикає й тут); позиції в порядку гостя з назвами розділів; «Я візьму це» — зображення кнопки. Позначок у превʼю немає й бути не може (ADR-040). Гостьова v2 ще не намальована, тож це суть сторінки, а не її пікселі. «Показати, як бачить гість» — вікно поверх списку, а не окремий маршрут.
- `ReorderV2` — «Змінити порядок» (V3): окремий режим, щоб перетягування не заважало свайпу. Розділи й «Інше», усередині — лише актуальні позиції (гості бачать тільки їх): перетягування за ручку (dnd-kit, мишею, пальцем і клавіатурою) і кнопки «Вище / Нижче» з живим рядком для зчитувача; фокус після кнопки лишається на тій самій позиції. Позиції між розділами переносить поле «Розділ» у формі. Запит — наявні `reorder_items` / `reorder_sections`; куплене й подароване стає слідом за актуальним, щоб місця лишались унікальними й v1 показувала той самий порядок. Без мережі режим недоступний.
- `AppearanceSheetV2` — оформлення списку (ADR-034) у формі v2: «Без оформлення», вбудовані, свої з видаленням, «Новий вигляд» з відтінком і живим прикладом.
- `ListSettingsV2` — назва, повідомлення гостям, дата, валюта й «Видалити список». Видалення має три ваги (F3): список, посилання на який ніхто не відкривав (`fetchListViews` у `lib/shares.ts` — сума `view_count` його посилань, зокрема відкликаних), іде тостом «Відмінити» на головній; відкривали — назву треба вписати рукою; не вдалося дізнатися — теж вписати. Вмикається за переглядами посилань, а не за позначками, щоб діалог не видав сюрприз.
- Свайп ліворуч по картці (лише дотик і перо) відкриває «Видалити» — те саме видалення з «Відмінити», прискорювач до меню «⋯» (F1).

`ListsV2` приймає зі сторінки списку стан історії: `deleteList` — видалити тостом «Відмінити» (відлік ставиться таймером: у StrictMode ефект проганяється двічі, і прибирання першого проходу довело б видалення до кінця одразу), `deletedTitle` — «Список «…» видалено». Порожня головна вперше показує «З чого почнемо?» (Q2): «Вставити посилання на річ» створює список «Мої бажання» й відкриває його з формою позиції (перейменувати — у налаштуваннях; чернеток без назви ще немає, крок 4), «Створити список до свята» веде в новий список, «Пропустити» — до шаблонів свят. Показано — `wl.v2.firstRunDone` у `localStorage`.

Спільне, що виросло з цього кроку: `lib/undo.ts` і `lib/variants.ts` (з `components/UndoToast.tsx` і `components/VariantsField.tsx`, які тепер їх лише реекспортують), `lib/order.ts` (ручний порядок і групи без клієнта бази — з `sections.ts`, який їх реекспортує), тип `Section` у `lib/types.ts`, `moneyShort` у `lib/format.ts` («1 240 грн» без «,00»).

**«Мої посилання» й «Налаштування» (крок 3в, потоки D, I).** Після них кожен екран власника v1 має пару у v2, і заглушка `SoonV2` зникла; невідома адреса — `PlaceholderV2` з дорогою назад.

- `SharesV2` — «Мої посилання»: два блоки, «Діють» і «Уже не діють» (відкликані й протерміновані). Картка — назва, «Зі списку «…»», «6 позицій · 23 перегляди · діє до 20 грудня» і тег стану. Живим — «Копіювати» й «Відкликати», мертвим — лише «Видалити». Назву списку дає `fetchSharesOverview` з `lib/shares.ts` — вкладення `lists(title)` у той самий запит; якщо сервер вкладення не прийме, картки лишаються без назви списку. Перегляди — не позначки й нічого про них не кажуть, тому дозволені; поруч немає нічого, що з позначками корелює (ADR-040). «Скопійовано» — пігулка на 2 с; браузер не дав скопіювати — вікно з адресою, щоб скопіювати руками. Копії без мережі тут немає: токени не кешуються. Порожній стан називає кнопки тими самими ключами, що й на кнопках («Поділитися», «Створити посилання»). На вузькій картці (міряє container query, а не вікно — ширину задає сітка) «Видалити» переходить під дві інші кнопки на всю ширину.
- `SettingsV2` — «Налаштування»: профіль (літера й пошта), «Доступність» із тумблером високої контрастності над «Кольорами» (приглушений, коли контраст увімкнений у системі), плитки схем, тема, мова, «Застосунок на телефоні» (на телефоні — встановлення чи інструкція, на десктопі — QR-код з адресою застосунку), «Мої дані», перемикач версії дизайну й акаунт із виходом. Усе застосовується одразу й зберігається тими самими `useTheme` і `useI18n`, що й у v1 (схема й тема — у профілі); вибір версії лишається в браузері. Видалення акаунта й сповіщень (P) ще немає.

**Після свята й архів (крок 4а, потоки M, S3, U; ADR-045).** Без міграції — лише наявна `lists.is_archived` і звичайні вставки власника.

- Картка «Як минуло свято?» (`AfterEventCardV2`) стоїть вгорі сторінки списку з наступного дня після `event_date`, поки список не в архіві. Кроки: «Позначити отримане», «Перенести, що ще хочу», «Повторити на 2027», «Архівувати» і «Пізніше». Коли показувати, вирішує `afterEventDue` з `lib/afterEvent.ts`. «Пізніше» живе в `localStorage` (`wl.v2.afterEvent.<id>`): 3 дні, потім картка повертається один раз, друге «Пізніше» ховає її назовсім.
- `ReceivedSheetV2` — нічого не позначено наперед (ADR-040). Позначене стає «Подаровано» операцією `status` офлайн-черги — тим самим шляхом, що й меню позиції.
- `CarrySheetV2` — копії актуальних позицій (`copyInput`) у новий список (`createListWithItems`) чи в наявний не архівний (`copyItems` у `lib/db.ts`). Оригінали й позначки на них не рухаються.
- `RepeatSheetV2` — `repeatList` у `lib/db.ts`: список із тим самим повідомленням, валютою й оформленням, розділи по одному (щоб зіставити старі й нові `id`), копії на тих самих місцях. Не вдалося — новий список видаляється, як в імпорті. Рік у назві посуває `repeatTitle`, дату — `nextYear`.
- Архів — `setListArchived`. На архівному списку немає «Поділитися», «+», «Змінити порядок», оформлення й нових розділів. Згори — `ArchivedNoteV2` з «Повернути з архіву», у меню — «Повторити» й «Повернути». Головна збирає архівні в згорнутий «Архів · N», а минулі з нерозібраним ставить згори свого блоку. `NewListV2` з минулою датою пропонує «Створити як архів».
- Гостей це не зачіпає: посилання на архівний список працюють як і раніше, v1 прапорця не знає.

**Чернетки й «Поділитися» з інших застосунків (крок 4б, потік L; ADR-046).**

- Валюта позиції (ADR-051) — вибір поруч із ціною в `ItemSheetV2` (усталено — валюта списку; ціну з магазину форма бере разом із її валютою, якщо знає її). Правило «своя або списку» — `itemCurrency` у `lib/itemsView.ts`; там само сума по валютах (`totalsOf` → `foreign`), сортування й діапазон ціни лише в одній валюті. `ListV2` показує «1 240 zł + 85 €» і, коли є інша валюта, підказку «≈ … за курсом НБП від …» (`useFxRates` з `lib/fx.ts` читає `fx_rates` раз на сесію, `approxTotal` рахує через злотий). Гостьова сторінка (спільна для `/s/` і `/l/`) і картка v1 показують валюту позиції з `get_shared_list` чи з рядка `items`.
- Ціна не у валюті списку — під полем ціни підказка «≈ 1 960 zł за курсом НБП від …» (`useFxRates` + `approxTotal`, ті самі, що під сумою списку). Курс тягнеться, лише коли валюта інша й ціна вписана; без курсу в `fx_rates` чи без мережі підказки немає. Зберігається ціна як вписана.
- Фото в `ItemSheetV2` — поле `image_url` посиланням (як у v1): перевірка повторює `check` у таблиці (`http(s)://`, до 2048), адреса картинки не нормалізується — мітки в запиті часто частина її адреси на CDN. Мініатюра під полем (крім нової позиції з превʼю згори, де фото вже є); картинка, що не відкрилась, — попередження, не помилка. «Заповнити з посилання» під полем посилання викликає той самий `parseUrl` і дописує лише порожні поля — так фото з магазину можна дотягнути й для збереженої позиції.
- Дата у v2 — `DateFieldV2` (`AuthPartsV2.tsx`): текстове поле з `inputMode="numeric"` і маскою «ДД.ММ.РРРР» (`lib/dateText.ts`) замість `<input type="date">`, який на Android відкриває лише календар. Календар — значок праворуч, під ним прозорий рідний `<input type="date">` (`showPicker()` на натиск). Назовні значення те саме, `YYYY-MM-DD` чи порожньо; неповна дата — порожньо й підказка під полем.
- Чернетка — позиція з `needs_title`: у назві адреса (`draftTitle` з `lib/itemsView.ts`), поруч мітка «Потрібна назва». `ItemSheetV2` пропонує «Зберегти чернетку», коли посилання є, а назви немає, — після збою парсера чи й без нього. Відкрита чернетка має порожнє поле назви, а назва знімає позначку явно. `ListV2` показує чернетки згори окремою групою. У «Поділитися», превʼю й «Змінити порядок» їх немає — туди йде `shareable`, актуальне без чернеток.
- Гостей стереже база: тригер не пускає чернетку в `share_items`. Інтерфейс v2 лише не пропонує того, що база однаково відкине.
- `/add` — `AddV2`, без каркаса, за `RequireAuthV2`: без входу веде на вхід із `next`, що несе поширене. Маніфест (`vite.config.ts`) має `share_target` — GET на `/add` з `title`, `text`, `url`. `fromShare` з `lib/shareTarget.ts` зводить їх до адреси й назви. Параметри одразу прибираються з адреси. Позиція створюється операцією `create` офлайн-черги, тож без мережі лягає в чергу: відправить її каркас v2 (`useOutbox`), щойно людина відкриє застосунок із мережею. Список на вибір — свіжий, а без мережі — з офлайн-копії. Останній вибраний — `wl.v2.lastList` у `localStorage`.
- `/add` у таблиці v1 — `AddBridgeV1`: пропонує перемкнутися на v2 з тим самим поширеним (`designSwitchHref`) або піти до списків.
- Service Worker віддає `/add` з кешованої оболонки, як будь-яку адресу застосунку. Поширене — не таємниця: це адреса й назва товару.

**Щорічні свята (крок 4в, потік U3; ADR-047).** Позначка `lists.repeats_yearly` у найсвіжішого списку «ряду».

- Перемикач `YearlySwitchV2` (`CommonV2.tsx`) стоїть у `NewListV2`, `ListSettingsV2` і `RepeatSheetV2`: без дати приглушений, з датою пише «Нагадаємо за місяць до …». Шаблони «День народження» й «Новий рік» передають `yearly: true`.
- `ListsV2` згори показує нагадування. `yearlyDue` з `lib/afterEvent.ts` вирішує, чи до найближчої річниці (`nextOccurrence`) не більше 30 днів і чи не сказали «Не цього разу» саме для неї (`wl.v2.yearly.<id>`). «Повторити на …» веде на сторінку списку зі станом `repeat`. `ListV2` відкриває `RepeatSheetV2`, щойно позиції завантажились.
- Повтор іде на найближчу річницю (`repeatTarget`), рік у назві замінюється на її рік. `repeatList` переносить позначку: новому — за вибором, старому — `false`.

**Перевірка посилань у v2 (крок 4г-1, потік R; ADR-048).** Висновки пише сервіс `wishlist-jobs` (див. «Потоки»); v2 лише читає поля `link_*` разом із позицією.

- `ItemCardV2` (`ListPartsV2.tsx`) на актуальній позиції показує тег «Сторінки немає» (`gone`, тон небезпеки), «Немає в наявності» (`out`, нейтральний) чи «Ціна змінилась» — коли ціна з магазину відрізняється від ціни в списку на 15 % і більше. Різницю рахує `linkPriceChange` з `lib/itemsView.ts`, у мінорних одиницях; іншу валюту чи нульову ціну не порівнює, а позиція без своєї ціни мітки не отримує — лише підказку в діалозі.
- `ItemSheetV2` у зміні позиції показує блок `.v2-linkcheck`: «Сторінки немає» — «Замінити посилання», «Шукати деінде» (пошук назви в Google) і «Прибрати зі списку» (те саме видалення з «Відмінити»); «Немає в наявності» — «Шукати деінде»; інша ціна — «У магазині зараз …» з «Оновити ціну», яке лише підставляє число в поле: зберігає людина. Дата перевірки — дрібним рядком.
- v1 полів не знає й нічого не показує.

**Сповіщення у v2 (крок 4г-2, потік P; ADR-049).** `NotifyV2.tsx`, логіка — у `lib/notifications.ts` (дані, push на пристрої) і `lib/notifyRules.ts` (чисті правила: вибір за замовчуванням, прапорці).

- `NotifyCardV2` — картка «Сповіщення» в Налаштуваннях (`/settings#notifications`). Не ввімкнено — пояснення й «Увімкнути сповіщення». Ввімкнено — перемикач «Push на цьому пристрої», події з пігулками Push / Пошта, «Безпека акаунта · Пошта · завжди», тиша, адреса листів, плашка «Про те, що взяли гості, сповіщень немає» (ADR-040) і «Вимкнути всі сповіщення».
- Push неможливий (`pushSupport`: заборонено, браузер не вміє, iPhone без встановленого застосунку) — перемикач замінює пояснення, пігулки push приглушені (вимкнути можна, ввімкнути — ні), а якщо push немає на жодному пристрої, важливе саме переходить із push на пошту. Збірка без `VITE_VAPID_PUBLIC_KEY` push не показує зовсім.
- `NotifyAskV2` — запит у контексті (P1) під діями аркуша «Посилання готове»: «Увімкнути сповіщення» чи «Не зараз» (`wl.v2.notifyAsked` у `localStorage` — більше не питати на цьому пристрої). Показується, лише поки нічого не ввімкнено.
- Пояс (`time_zone`) оновлюється щоразу, коли людина відкриває Налаштування з іншим поясом пристрою.

Модальні вікна v2 — `SheetV2` на рідному `<dialog>`: нижній лист на телефоні, по центру на десктопі.

Вибір версії **не** їде в профіль і лишається в браузері: поки v2 наповнюється, ввімкнення її на телефоні не має міняти застосунок на ноутбуці.

Імена файлів у `designs/` унікальні на весь репозиторій: `scripts/place-files.ps1` розкладає за іменем і двох `Routes.tsx` розкласти не може.


### Аудит контрасту

`npm run check:contrast` читає `tokens.css` і рахує 25 пар «фарба на фарбі» × 12 палітр = 300 перевірок: 4,5:1 для тексту, 3:1 для нетекстових індикаторів (смужки пріоритету, кільце фокуса). Числа беруться з тих самих токенів, що й у застосунку, тож таблиця не може розійтися з тим, що бачить людина. У CI стоїть **перед** збіркою — зламаний контраст видно за секунди.

Додав пару кольорів у компонентах — додай її і в `PAIRS`, інакше вона лишиться неперевіреною.

### Шрифти

Самохостяться через `@fontsource-variable`, не з CDN: CSP пускає лише `'self'`, а офлайн-оболонка має відкриватися без мережі. Заголовки — Rubik 800, текст — Manrope; обидві покривають `cyrillic`, `cyrillic-ext` і `latin-ext`, тобто всі три мови. Арабиця й іврит, які Rubik возить із собою, у precache не потрапляють (`globIgnores` у `vite.config.ts`). Жоден шрифт не вбудовується в CSS як `data:` URI: усталений поріг Vite (4 КБ) інлайнив `cyrillic-ext` Manrope — підмножину зі знаком ₴, — а CSP `font-src 'self'` мовчки блокував його в бою. Тепер `assetsInlineLimit` явно виключає шрифти, і `npm run check:pwa` падає, якщо вбудований шрифт знову зʼявиться.

## Заголовки безпеки

`vercel.json` віддає на всі шляхи `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` і `Permissions-Policy`, а на `/s/*` і `/l/*` ще й `X-Robots-Tag: noindex`.

CSP тут не косметика: секрет гостьового посилання лежить у самій адресі, тож будь-який XSS означав би витік токенів. Політика:

- `default-src 'self'` — усе своє; `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`.
- Гостьові сторінки `/s/*` (v1) і `/l/*` (v2) віддаються із заголовком `X-Robots-Tag: noindex, nofollow, noarchive`, а `robots.txt` просить не сканувати їх. Токен у пошуковому індексі означав би, що посилання бачить будь-хто.
- `Referrer-Policy: strict-origin-when-cross-origin` — за межі сайту йде лише домен, без шляху. У шляху гостьової адреси токен, а в особистому посиланні ще й ключ гостя; `unsafe-url` чи `no-referrer-when-downgrade` віддали б їх магазину, на який гість натисне. `npm run check:pwa` пускає лише політики, що шлях не віддають.
- `script-src 'self'` плюс хеш єдиного інлайнового скрипта — того, що застосовує тему до першого рендера. `'unsafe-inline'` немає, інакше CSP не захищав би ні від чого. Хеш звіряє `npm run check:pwa`: зміниш скрипт — CI скаже, який хеш підставити.
- `style-src 'self' 'unsafe-inline'` — React ставить частину стилів атрибутом `style`.
- `img-src 'self' https: data:` — картинки товарів беруться з будь-якого магазину.
- `connect-src` — лише Supabase і парсер на Cloud Run.
- `worker-src 'self'` і `manifest-src 'self'` — для Service Worker і маніфесту.

Перевірено на зібраному застосунку з реальним заголовком: жодного порушення під час входу, роботи зі списком і перегляду гостьового посилання; інжектований інлайновий скрипт і скрипт зі стороннього домену заблоковано.

## Захист роутів

`<RequireAuth>` — обгортка, що читає сесію Supabase. Поки сесія завантажується — скелетон, не редірект (інакше при F5 користувача викидає на логін). Немає сесії → `/login?next=<шлях>`.

Значення `next` приходить з адресного рядка, тож його може підставити будь-хто. Сторінка входу пропускає його через `safeNext` (`src/lib/safeNext.ts`): рядок розбирається тим самим парсером URL, що й у браузері, і приймається лише якщо лишається в межах сайту. Інакше — `/lists`.

Публічні роути: `/login`, `/register`, `/reset`, `/s/:token`, `/l/:token` (з `/g/:key` або без). Усе інше — за автентифікацією.
