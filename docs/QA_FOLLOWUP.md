## Продукт і пріоритети

Продукт — приватні списки бажань з вибірковим поширенням, анонімними бронями та спільними подарунками. Основні ролі: власник, інший авторизований користувач, гість без ключа, гість із ключем, організатор збору, учасник збору. Ключові ризики: розкриття сюрпризу власнику, доступ до чужих даних, втрата офлайн-змін, спотворення ціни та неможливість відновити бронь.

Автоматизація охоплює всі основні модулі за наведеною картою. Це **не твердження про 100% шляхів, коду або комбінацій**. Кожна зелена перевірка підтверджує лише свої умови й оракул. Покриття реального доставлення листів/push, OAuth провайдера та встановленого PWA не підміняємо тестами із заглушками.

### BUG-QA-23 — ціна JSON втрачає десяткову крапку

**Де:** `transfer.ts`, `parseJsonFile → rowToItem → parsePrice`.
**Кроки:** імпортувати `{"items":[{"title":"Lamp","price":1.234}]}`.
**Очікувано:** 1.23 згідно з округленням імпорту до копійок (або явне попередження про надлишкову точність), ніколи 1234.
**Факт:** 1234 без попередження; 12.345 → 12345, 0.125 → очищена ціна.
**Причина:** JSON number перетворюється на рядок і проходить правила локалізованого групування розрядів.
**Рекомендація:** зберігати тип JSON-числа до валідації та округлення; локалізоване групування застосовувати лише до тексту. Не змінювати задуманий CSV `1.234` = 1234.

### BUG-QA-24 — формат дати прийнято за календарну валідність

**Де:** `transfer.ts`, `checkList`.
**Кроки:** імпортувати `{"list":{"event_date":"2026-02-29"},"items":[{"title":"Lamp"}]}`.
**Очікувано:** попередження `transfer.issues.eventDate`, очищена дата, решта списку придатна.
**Факт:** дата прийнята без попереджень. Те саме для 1900-02-29, 31 квітня, місяців 00/13 і дня 00. Форма створення вже відкидає такі дати.
**Наслідок:** підготовлений імпорт містить значення, непридатне для колонки PostgreSQL `date`; UI-прохід із живою БД у цьому тесті не використано.
**Рекомендація:** перевіряти календарну дату, а не лише regex форми ISO.

### BUG-QA-25 — обрізання Unicode

**Де:** `transfer.ts`, обрізання `note` і `section` через `slice`.
**Кроки:** імпортувати нотатку з 999 символів `a` і `🎁tail`; для розділу — 59 `a` і той самий хвіст.
**Очікувано:** валідний Unicode після обрізання, без половини emoji.
**Факт:** останній символ — самотній high surrogate `\uD83C`. PostgreSQL не може зберегти його як валідний UTF-8; тут підтверджено пошкодження результату парсингу, не фактичну відмову мережевого імпорту.
**Рекомендація:** обрізання за code points із узгодженими обмеженнями БД; перевірити також назву списку, опис і ознаки.

### BUG-QA-26 — аварія перетворення об'єкта в рядок

**Кроки:** `parseJsonFile('{"items":[{"title":{"toString":null}}]}', 'QA')`.
**Очікувано:** результат із помилкою типу/рядка, без винятку.
**Факт:** `TypeError: Cannot convert object to primitive value` у `trimmed`.
**Вплив:** UI має зовнішній catch, тому це не доказ падіння всього застосунку; файл переривається з технічною помилкою замість пояснення поля.
**Рекомендація:** явний whitelist примітивних типів, об'єкти полів не коерсити через `String`.

### BUG-QA-27 — JSON-LD неправильних типів

**Кроки:** магазин повертає `<script type="application/ld+json">{"@type":7}</script><title>Fallback lamp</title>`; викликати `/parse`. Другий клас: `{"@type":"Product","name":{"text":"Lamp"}}`.
**Очікувано:** ігнорувати неправильні поля, повернути 200 з резервною назвою й `partial:true`.
**Факт:** HTTP 500. `@type` число/boolean не підтримує `in`, `name` об'єкт/масив/число потрапляє в `re.sub`.
**Рекомендація:** перевіряти типи до використання і дозволяти fallback окремого поля. HTTP-тест використовує справжні FastAPI й extract; завантаження сторінки та auth замінені фікстурами.

### BUG-QA-28 — велике JSON-число

**Кроки:** Product із `offers.price`, що містить ціле з 309 або 400 дев'яток, на `/parse`.
**Очікувано:** 200, `price:null`, `partial:true`.
**Факт:** 500: `math.isfinite(raw)` на Python int кидає OverflowError ще до захисної перевірки float.
**Рекомендація:** обмежувати розмір/діапазон перед конвертацією або обробляти OverflowError.

### BUG-QA-29 — мінус стає плюсом

**Кроки:** `parse_price('-49,90 zł')`, `parse_price('-0.01')`.
**Очікувано:** None — від'ємна ціна невалідна, як уже реалізовано для числового -5.
**Факт:** 49.9 та 0.01: regex починає захоплення з цифри й губить знак.
**Рекомендація:** розпізнавати й відкидати від'ємні цінові токени до очищення рядка.

### BUG-QA-30 — неправдиве підтвердження офлайн-збереження

**Де:** `outbox.ts`: `run` → `enqueue`; `idb.ts`: `openDb`.
**Умови:** REST недоступний, `indexedDB.open` кидає SecurityError (наприклад, сховище заборонене).
**Кроки тесту:** заблокувати REST через Playwright route; підмінити лише `IDBFactory.prototype.open`; викликати справжній `outbox.run` для delete; прочитати лічильник черги. Підміна відновлюється в finally.
**Очікувано:** відмова, яку UI може показати; не `queued` без збереженого запису.
**Факт (код і локальний запуск модуля):** `openDb` повертає null; `enqueue` мовчки завершується; `run` повертає `queued`, pending = 0. Після reload локальну зміну немає звідки повторити.
**Рекомендація:** enqueue мусить підтверджувати commit IndexedDB; невдале відкриття/транзакція має відхиляти операцію. Перевірити й false від `txDone`, який зараз ігнорується.

## Запуски й трактування результатів

Локально, Python 3.12 / Node 24:

- `npm run test:logic`: 235 виконаних = 223 звичайних успішних + 12 очікуваних падінь нових дефектів. Playwright підсумовує очікувані падіння як passed; це **не означає, що баги виправлені**.
- `QA_STRICT=1 npm run test:logic -- qa-data-integrity`: 30 passed, **12 failed**; усі падіння відповідають BUG-QA-23…26.
- `pytest`: **314 passed, 10 xfailed**. У середовищі із системним SOCKS proxy його env змінні прибрано лише з процесу pytest; мережеві відповіді сервісів у цих тестах підмінено.
- BUG-QA-30: зібраний esbuild справжній `outbox.ts` при `fetch → TypeError("Failed to fetch")` і `indexedDB.open → SecurityError` повернув `{"result":"queued","pending":0}`. Жодного мережевого запиту не зроблено.
- `npm run typecheck`, `npm run build`, `npm run check:pwa`, `npm run check:i18n`, `npm run check:contrast` — успішно.
- Локально немає Docker/Supabase, завантаження Chromium повернуло пошкоджений архів. Повний pgTAP/браузерний прогін має виконати GitHub Actions після публікації гілки. Публікація заблокована: GitHub повернув `403 Resource not accessible by integration` на створення tree і branch; гілка та PR віддалено не створені. Початковий main мав [успішний CI](https://github.com/yozh150991/Wishlist_personal/actions/runs/39759662560).

Знайдені дефекти не приховані `skip`: використовуються `test.fail` і `xfail(strict=True)` за ADR-069. Неочікуваний успіх робить CI червоним і вимагає прибрати позначку. Python xfail дозволений лише для AssertionError; TypeError та інші помилки самого тесту не приховуються. Для Playwright позначка стоїть після успішних передумов. Після виправлення зняти позначку й оновити цей звіт.

```bash
# Швидка регресія без браузера/БД
cd app
npm ci
npm run test:logic
# Показати відомі дефекти як справжні падіння (Linux/macOS)
QA_STRICT=1 npm run test:logic -- qa-data-integrity
# PowerShell: $env:QA_STRICT='1'; npm run test:logic -- qa-data-integrity
# Після цього: Remove-Item Env:QA_STRICT

# Браузерна інтеграція — лише на локальному Supabase за TESTING.md
E2E_LOCALDB=1 npx playwright test qa-storage-resilience
# QA_STRICT=1 знімає expected-failure позначку також для BUG-QA-30.

cd ../services/parser
pip install -r requirements-dev.txt
pytest
pytest tests/test_qa_resilience.py --runxfail  # навмисно червоний до виправлень
```

Наступні пріоритети: виправити втрату офлайн-операцій і прогнати браузерне підтвердження; виправити спотворення грошей; нормалізувати вхід імпорту й JSON-LD; окремо прогнати конкурентні бронювання, квоти сховища, реальні email/push та фізичні мобільні браузери.
