# Правила для AI-агентів у цьому репозиторії

Читай цей файл перед будь-якою зміною коду.

## 1. Документація — не додаток, а частина роботи

Будь-яка зміна коду, що впливає на поведінку, схему або API, **у тому самому коміті** оновлює відповідний `.md`:

| Що змінив | Що оновлюєш |
|---|---|
| Таблицю, колонку, RLS-політику, індекс | `docs/DATA_MODEL.md` |
| RPC-функцію або ендпоінт парсера | `docs/API.md` |
| Компонент, потік даних, залежність | `docs/ARCHITECTURE.md` |
| Змінну оточення | `.env.example` + `docs/SETUP.md` або `docs/DEPLOY.md` |
| Обрав технологію / підхід всупереч очевидному | новий ADR у `docs/DECISIONS.md` |
| Будь-яку помітну для користувача зміну | `CHANGELOG.md` |
| Завершив етап | `docs/ROADMAP.md` + `README.md` (статус) |

Код без оновленої документації вважається незавершеним.

## 2. Формат ADR

Рішення дописуються в кінець `docs/DECISIONS.md`, ніколи не редагуються заднім числом.
Якщо рішення скасовано — старий ADR лишається, статус міняється на `Скасовано ADR-XXX`, додається новий.

```
## ADR-012: Коротка назва
Дата: 2026-09-09
Статус: Прийнято | Скасовано ADR-018 | Замінює ADR-004
Контекст: ...
Рішення: ...
Наслідки: ...
Відхилені альтернативи: ...
```

## 3. Інваріанти, які не можна порушувати

Ці правила захищають приватність — це суть продукту.

1. **Головний список ніколи не доступний нікому, крім власника.** Жоден запит, RPC чи в'ю не повертає `lists` або `items` за межі `auth.uid() = owner_id`.
2. **Власник не бачить бронювань.** Немає RLS-політики, RPC чи в'ю, які дають власнику доступ до `reservations`. Це навмисне обмеження — не «баг», який треба «полагодити».
3. **Гостьовий доступ іде виключно через `SECURITY DEFINER` RPC з токеном шеру.** Anon-роль не має прямого `SELECT` на жодну таблицю.
4. **Кожна нова функція в схемі `public` отримує гранти явно.** PostgREST публікує схему як RPC, а Supabase через default privileges видає `EXECUTE` на кожну нову функцію ролям `anon`, `authenticated` і `service_role` **окремими грантами**, не лише `PUBLIC`. Тому `revoke ... from public` недостатньо — відкликати треба в конкретних ролей:
   ```sql
   revoke execute on function public.f(...) from public, anon;             -- функція власника
   revoke execute on function public.f(...) from public, anon, authenticated; -- внутрішня
   ```
   Функцію, яку викликає `SECURITY INVOKER` функція, викликач теж мусить мати право виконувати. Тест `supabase/tests/database/01_schema_guards.test.sql` падає на кожній функції, доступній зайвим ролям — його список дозволених функцій оновлюється свідомо, разом із міграцією.
5. **Токени шеру не логуються й не кешуються** — ні в аналітику, ні в помилки, ні в консоль, ні в кеш Service Worker. Гостьові сторінки `/s/*` виключено з навігації Service Worker у `vite.config.ts`; `npm run check:pwa` падає, якщо це виключення зникне.
6. **Парсер не ходить у приватні мережі.** SSRF-захист обов'язковий, тести на нього обов'язкові.

Якщо задача вимагає порушити інваріант — зупинись і спитай користувача, а не обходь.

Інваріанти перевіряються pgTAP-тестами в `supabase/tests/database/` (TESTING.md). Міграція, після якої `npx supabase test db` червоний, не пушиться. CI (`.github/workflows/ci.yml`) проганяє pgTAP, pytest і Playwright на кожен push і pull request. `main` захищено: зміни лише через PR із зеленим CI (DEPLOY.md, розділ 8). Робота йде в гілках; назва гілки — `feat/…`, `fix/…`, `docs/…`, `test/…`.

## 4. Стиль коду

- TypeScript `strict: true`. `any` заборонений, крім `unknown` + звуження типу.
- Дві конфігурації: `tsconfig.json` покриває `src/` і не має типів Node — щоб `process` не можна було випадково вжити в коді браузера; `tsconfig.test.json` покриває `tests/` і `playwright.config.ts`. `npm run typecheck` прогонить обидві. Новий файл поза `src/` не перевіряється, поки не потрапить в `include` однієї з них.
- Типи БД генеруються: `supabase gen types typescript --local > app/src/types/database.ts`. Не редагувати вручну.
- Міграції тільки додаткові, іменування **`<14-значний timestamp>_short_name.sql`** (напр. `20260910120000_init.sql`) — саме цей формат розпізнає Supabase CLI, і саме timestamp визначає порядок застосування. Файли з іншими іменами CLI мовчки ігнорує. Створювати через `npx supabase migration new <name>`, а не вручну. Не редагувати вже застосовані міграції.
- Тексти інтерфейсу — тільки через i18n-ключі (`uk`/`pl`/`en`). Хардкод рядків у JSX — помилка ревʼю.
- Скрипти `.ps1` — тільки ASCII в коді й повідомленнях. Windows PowerShell 5.1 читає їх у системному кодуванні, і кирилиця без UTF-8 BOM ламає розбір. Обмеження стосується лише PowerShell: у `.ts`, `.tsx`, `.sql` і `.md` кирилиця нормальна.
- Кожне `check`-обмеження в БД має відповідник у формі: `min`/`max`/`maxLength` на полі плюс перевірка перед відправкою. База лишається останнім рубежем, але користувач не має дізнаватися про межі з `400 Bad Request`. Додав обмеження в міграції — додай і у форму.
- Помилки для людини — `errorText(e, t)` з `lib/errors.ts`, не `String(e)`: помилки Supabase — обʼєкти, і `String` дає «[object Object]». Сторінка з помилкою завантаження не показує порожній стан.
- Гроші: у БД `numeric(12,2)`, у JS ніколи не `float` для арифметики — рахувати в мінорних одиницях.
- Форми, зокрема в діалогах, — `<form noValidate onSubmit>` з `<button type="submit">`, а не `onKeyDown` з перевіркою Enter на полях. Решта кнопок усередині форми («Скасувати», «Заповнити», «Копіювати») — обовʼязково `type="button"`, інакше кожна з них відправляє форму. `submit` на початку перевіряє `busy`: подвійний Enter не має створити два записи. Поля автентифікації мають `autoComplete`: `username` для пошти, `current-password` для входу, `new-password` для нового пароля. Без цього менеджери паролів не пропонують зберегти пароль.

## 5. Робота з користувачем

Власник проєкту (Ihor) працює ітеративно і просить **повні готові файли**, а не фрагменти. Віддавай файл цілком, з шляхом у заголовку.

Новий файл, якого немає в таблиці `scripts/place-files.ps1`, додавай і туди — інакше скрипт його не розкладе.

## 6. Бойове середовище

Застосунок опубліковано (DEPLOY.md), і база Supabase одна — вона ж бойова. Звідси:
- застосовані міграції не редагуються, лише нові файли;
- E2E-тести ходять у ту саму базу, тому запускаються під окремим тестовим акаунтом;
- зміни парсера доходять до користувачів лише після `gcloud run deploy`, зміни фронтенду — після `git push` у `main`.
