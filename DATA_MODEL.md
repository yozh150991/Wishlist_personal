# Модель даних

Джерело істини — `supabase/migrations/*.sql`. Цей файл пояснює *чому*.

## Схема

```
auth.users
    │
    ├──1:1── profiles          (locale, theme, default_currency)
    │
    └──1:N── lists             (title, currency, event_date, is_archived)
                 │
                 ├──1:N── items       (title, url?, price?, quantity,
                 │           │         priority, note, image_url, status)
                 │           │
                 │           ├──N:M── share_items ──N:1── shares
                 │           │
                 │           └──1:N── reservations  ← ізольовано від власника
                 │
                 └──1:N── shares      (token, hide_prices, expires_at, revoked_at)
```

## Таблиці

### `lists`
Користувач має довільну кількість списків. `currency` — одна на список: змішувати валюти в одному списку означало б курси, конвертацію і застарілі дані (ADR-005). `event_date` вмикає підказку «підбити підсумки» після дати.

### `items`
`url` і `price` — nullable. Це пряма вимога: користувач може додати «навушники, приблизно 400 zł» або взагалі без ціни.

`owner_id` денормалізовано з `lists.owner_id`. RLS-політика `owner_id = auth.uid()` виконується за індексом без JOIN до `lists` на кожен рядок. Синхронізує тригер `items_sync_owner` — вручну колонку не пишемо.

`status`:
| Значення | Сенс |
|---|---|
| `active` | актуально, показується гостям |
| `purchased` | власник купив собі сам |
| `gifted` | подаровано (підсумки після події) |

Позиції зі статусом `purchased`/`gifted` **не показуються в спільних посиланнях** — щоб гість не купив те, що вже є.

### `shares`
`token` — 16 випадкових байтів у base64url (22 символи, ~128 біт). Перебір нереальний, тому окремого пароля не треба.

Посилання **живе**: `get_shared_list` щоразу читає актуальні `items`. Видалив позицію в себе — вона зникла й у гостей (через `ON DELETE CASCADE` на `share_items.item_id`).

Відкликання — `revoked_at`, а не `DELETE`: збереження історії й статистики переглядів.

### `reservations`
**Інваріант проєкту.** Таблиця має `ENABLE ROW LEVEL SECURITY` і **жодної політики**. У Postgres це означає «заборонено всім». Плюс явний `REVOKE ALL ... FROM authenticated`.

Читає й пише її тільки `SECURITY DEFINER` RPC для гостя. Власник не має жодного шляху дізнатися, що заброньовано — це властивість продукту, а не обмеження, яке треба обійти.

Обмеження, яке ми приймаємо свідомо: власник має токен і може відкрити посилання сам. Тому `get_shared_list` перевіряє `auth.uid() = share.owner_id` і повертає `reserved_qty: null`. У режимі інкогніто це не спрацює — див. ADR-009.

`guest_key` — випадковий UUID з `localStorage`. Не email, не імʼя, не IP. Потрібен лише щоб гість зняв свою бронь.

## Пагінація

Нескінченний скрол на **keyset-пагінації** (`list_items_page`), не на `OFFSET`. При `OFFSET` довантаження після додавання/видалення позиції дублює або губить рядки, і на великих списках сканування росте лінійно.

Курсор — пара `(значення_сортування, id)` останнього показаного рядка. `id` розриває нічию при однакових значеннях.

Розмір партії: `10 | 25 | 50 | 100`, за замовчуванням **25**. Перевіряється в RPC — довільні значення відхиляються.

## Індекси

| Індекс | Для чого |
|---|---|
| `items_list_created_idx (list_id, created_at desc, id desc)` | сортування за замовчуванням |
| `items_list_price_idx`, `items_list_title_idx` | альтернативні сортування |
| `items_list_status_idx` | фільтр по статусу |
| `items_title_trgm_idx` (GIN trgm) | пошук `ILIKE '%...%'` без seq scan |
| `shares.token` (unique) | пошук за токеном |
| `reservations_guest_idx (share_id, guest_key)` | «мої броні» гостя |

## Гроші

`numeric(12,2)` у БД. У JS сума рахується в мінорних одиницях (гроші як цілі), щоб не ловити `0.1 + 0.2`. Форматування — `Intl.NumberFormat` за локаллю користувача і валютою списку.

`list_totals()` окремо повертає `items_no_price` — щоб інтерфейс міг чесно написати «разом 1 240 zł, ще 3 позиції без ціни», а не робити вигляд, що сума повна.
